## Objetivo

Al terminar esta lección podrás crear un cliente de Supabase en una app Expo, explicar qué claves son públicas y cuáles nunca deben salir del servidor, y registrar, iniciar y cerrar sesión con email y contraseña.

**Prerrequisitos:** `08-autenticacion-backend/01-oauth2-oidc-y-jwt`

## Concepto

Supabase es un backend como servicio construido sobre PostgreSQL. Te da, listos para usar, un servidor de autenticación, una base de datos con API automática y un almacén de archivos. En esta etapa lo usas para que la app de notas tenga usuarios reales sin escribir un servidor desde cero.

### La analogía del edificio de oficinas

Imagina un edificio de oficinas. La dirección del edificio y el número de la recepción están impresos en todas las tarjetas de visita: son públicos, cualquiera puede presentarse. Lo que impide entrar donde no debes son los tornos y las cerraduras de cada planta. Y existe una llave maestra que solo tiene el personal de mantenimiento y que jamás se entrega a un visitante.

En Supabase:

- La **URL del proyecto** es la dirección del edificio.
- La **anon key** (en proyectos nuevos, la **publishable key**) es el número de la recepción: identifica tu proyecto y es **pública por diseño**.
- Las **políticas Row Level Security** son las cerraduras: deciden qué filas puede ver cada usuario. Las verás en la próxima lección.
- La **service role key** (o **secret key**) es la llave maestra: se salta todas las políticas. **Nunca va en la app**, solo en servidores que tú controlas.

### Crear el proyecto

1. Entra en https://supabase.com/dashboard y crea un proyecto nuevo. Elige una región cercana a tus usuarios y guarda la contraseña de la base de datos en tu gestor de contraseñas.
2. En **Project Settings, API** copia la URL del proyecto y la anon key (o publishable key).
3. En **Authentication, Providers** comprueba que **Email** está activo. Por defecto Supabase pide confirmar el email antes de permitir el inicio de sesión.

La guía oficial de autenticación está en https://supabase.com/docs/guides/auth y el tutorial para Expo en https://supabase.com/docs/guides/getting-started/tutorials/with-expo-react-native.

### Variables de entorno con `EXPO_PUBLIC_`

Expo carga automáticamente un archivo `.env` en la raíz del proyecto. Las variables cuyo nombre empieza por `EXPO_PUBLIC_` se sustituyen por su valor **dentro del bundle de JavaScript** al compilar.

```bash
# .env (add it to .gitignore anyway, so each developer uses their own project)
EXPO_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_KEY
```

Que vayan en el bundle significa que cualquiera que descargue tu app puede leerlas. Eso es aceptable para la URL y la anon key, porque son públicas por diseño. Es inaceptable para cualquier secreto: si alguna vez te ves escribiendo `EXPO_PUBLIC_SUPABASE_SERVICE_ROLE_KEY`, detente. Más detalles en https://docs.expo.dev/guides/environment-variables/.

### El cliente

Crea un único cliente en un módulo propio y reutilízalo en toda la app. En esta lección la sesión solo vive en memoria (`persistSession: false`): al cerrar la app hay que volver a iniciar sesión. En la lección de SecureStore aprenderás a guardarla de forma segura.

```ts
// src/lib/supabase.ts
import { createClient } from "@supabase/supabase-js";

const supabaseUrl = process.env.EXPO_PUBLIC_SUPABASE_URL;
const supabaseAnonKey = process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY;

if (!supabaseUrl || !supabaseAnonKey) {
  throw new Error("Missing EXPO_PUBLIC_SUPABASE_URL or EXPO_PUBLIC_SUPABASE_ANON_KEY");
}

export const supabase = createClient(supabaseUrl, supabaseAnonKey, {
  auth: {
    persistSession: false,
    autoRefreshToken: true,
    detectSessionInUrl: false,
  },
});
```

`detectSessionInUrl: false` le dice al cliente que no busque tokens en la URL del navegador, algo que solo tiene sentido en la web.

### Registro, inicio y cierre de sesión

```ts
// Sign up: creates the user. With email confirmation on, session is null until confirmed.
const { data, error } = await supabase.auth.signUp({ email, password });

// Sign in: returns a session with access_token and refresh_token.
const result = await supabase.auth.signInWithPassword({ email, password });

// Sign out: revokes the refresh token on the server and clears the local session.
await supabase.auth.signOut();
```

Todas las funciones devuelven `{ data, error }` en lugar de lanzar excepciones: comprueba siempre `error` antes de usar `data`.

### Escuchar los cambios de sesión

La sesión cambia por muchas razones: inicio de sesión, cierre, renovación automática del token. En lugar de consultar el estado a mano, suscríbete:

```ts
const { data } = supabase.auth.onAuthStateChange((event, session) => {
  console.log(event, session?.user.email);
});

// Later, for example when a component unmounts:
data.subscription.unsubscribe();
```

`event` vale, entre otros, `INITIAL_SESSION`, `SIGNED_IN`, `SIGNED_OUT` o `TOKEN_REFRESHED`. Tu navegación puede decidir con esto si muestra la pantalla de login o la lista de notas.

## Errores comunes

**Poner la service role key en la app.** El código funciona "mejor" porque ninguna política bloquea nada. Ocurre al copiar la primera clave que aparece en el panel. Se detecta buscando `service_role` o `SERVICE_ROLE` en el repositorio y decodificando la clave usada por la app: si su claim `role` vale `service_role`, cualquiera que descargue la app tiene acceso total. Rótala de inmediato desde el panel.

**Creer que `EXPO_PUBLIC_` oculta algo.** Se guarda un secreto en `.env` con ese prefijo pensando que el archivo `.env` no se publica. Ocurre porque se confunde "no está en Git" con "no está en la app". Se detecta buscando el valor en el bundle generado con `npx expo export`: las variables `EXPO_PUBLIC_` aparecen en texto plano.

**Ignorar `error` en las respuestas.** El código usa `data.user` directamente y falla con "Cannot read properties of null". Ocurre porque el cliente no lanza excepciones en errores de autenticación. Se detecta porque los fallos de login no muestran ningún mensaje. Comprueba siempre `error` primero.

**Esperar una sesión tras `signUp`.** Con la confirmación de email activa, `data.session` es `null` hasta que el usuario pulsa el enlace. Se detecta porque la app se queda en el registro sin avanzar; muestra un mensaje que pida revisar el correo.
