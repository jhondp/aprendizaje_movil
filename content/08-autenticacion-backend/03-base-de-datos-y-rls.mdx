## Objetivo

Al terminar esta lección podrás crear una tabla en Supabase, activar Row Level Security y escribir políticas que usan `auth.uid()` para que cada usuario solo acceda a sus propias notas.

**Prerrequisitos:** `08-autenticacion-backend/02-supabase-setup-y-auth`

## Concepto

Supabase expone cada tabla de tu base de datos como una API accesible con la anon key. Como esa clave es pública, cualquiera puede enviar consultas a tu proyecto. Lo único que separa "mis notas" de "todas las notas" es **Row Level Security (RLS)**: reglas que PostgreSQL evalúa en el servidor para cada fila, en cada consulta.

### La analogía de los buzones

Piensa en los buzones de un edificio. Todos están en el mismo mueble del portal y todos los vecinos tienen acceso al portal. Pero cada buzón tiene su cerradura, y tu llave solo abre el tuyo. La tabla `notes` es el mueble de buzones, la anon key te deja entrar al portal y las políticas RLS son las cerraduras: comparan tu identidad con el dueño de cada fila.

### Crear la tabla

En el panel de Supabase, abre **SQL Editor** y ejecuta:

```sql
create table public.notes (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  title text not null check (char_length(title) between 1 and 200),
  created_at timestamptz not null default now()
);
```

Fíjate en `user_id uuid not null default auth.uid()`. La función `auth.uid()` devuelve el identificador del usuario del token que acompaña la petición, ya verificado por Supabase. Al usarla como valor por defecto, la app ni siquiera necesita enviar `user_id` al insertar. `on delete cascade` borra las notas si se elimina la cuenta.

### Activar RLS

```sql
alter table public.notes enable row level security;
```

Con RLS activo y **ninguna política**, la tabla queda cerrada: toda consulta con la anon key devuelve cero filas. Es un punto de partida seguro. A partir de ahí abres, con políticas, exactamente lo que cada usuario necesita.

Las tablas creadas desde el editor visual (Table Editor) activan RLS por defecto, pero las creadas con SQL no. Por eso la lista de comprobación de esta lección insiste en revisarlo en cada tabla.

### Escribir políticas

Una política responde a la pregunta de la autorización: quién (`to`), qué acción (`for`) y sobre qué filas (`using` y `with check`).

```sql
create policy "Users can read their own notes"
on public.notes for select
to authenticated
using ((select auth.uid()) = user_id);

create policy "Users can create their own notes"
on public.notes for insert
to authenticated
with check ((select auth.uid()) = user_id);
```

- `to authenticated`: la política solo se aplica a peticiones con una sesión válida. Las peticiones anónimas no ven nada.
- `using (...)`: filtra las filas **existentes** que la consulta puede ver o tocar. Se usa en `select`, `update` y `delete`.
- `with check (...)`: valida las filas **nuevas o modificadas**. Se usa en `insert` y `update`. Sin ella, un usuario podría insertar una nota con el `user_id` de otra persona.
- `(select auth.uid())` en lugar de `auth.uid()`: el resultado es el mismo, pero PostgreSQL lo calcula una sola vez por consulta en vez de una vez por fila. La documentación lo recomienda por rendimiento.

Guía oficial: https://supabase.com/docs/guides/database/postgres/row-level-security.

### Consultar desde la app

Con las políticas en su sitio, la app pide notas sin filtrar por usuario, y aun así solo recibe las suyas:

```ts
const { data, error } = await supabase
  .from("notes")
  .select("id, title, created_at")
  .order("created_at", { ascending: false });

const { error: insertError } = await supabase.from("notes").insert({ title: "Comprar pan" });
```

Puedes añadir `.eq("user_id", userId)` para que la consulta use un índice, pero entiende que eso es una optimización, no seguridad: aunque borres esa línea, o alguien la cambie en una app modificada, RLS sigue filtrando en el servidor.

### Cómo probar tus políticas

No confíes en que "la app funciona". Prueba el caso negativo:

1. Crea dos usuarios de prueba, A y B.
2. Inicia sesión como A y crea una nota.
3. Inicia sesión como B y consulta `notes`: debe devolver una lista vacía, no un error.
4. Como B, intenta insertar una nota con `user_id` de A: debe fallar con un error de política (`new row violates row-level security policy`).

El panel de Supabase también muestra una advertencia en **Advisors, Security** para cada tabla pública sin RLS.

## Errores comunes

**Crear la tabla con SQL y olvidar activar RLS.** La app funciona perfectamente, pero cualquiera con la anon key puede leer y borrar todas las notas. Ocurre porque las tablas creadas con SQL no activan RLS solas. Se detecta en **Advisors, Security** o con la consulta `select tablename, rowsecurity from pg_tables where schemaname = 'public';`, que debe mostrar `true` en cada fila.

**Activar RLS sin políticas y pensar que la app está rota.** Todas las consultas devuelven una lista vacía, sin error. Ocurre porque RLS sin políticas deniega todo en silencio. Se detecta porque la tabla tiene filas en el panel (que usa privilegios de administrador) pero la app no ve ninguna.

**Olvidar `with check` en insert o update.** Un usuario puede insertar notas a nombre de otro o transferir las suyas. Ocurre porque `using` solo filtra filas existentes. Se detecta intentando, como usuario B, insertar una fila con el `user_id` de A: si funciona, falta `with check`.

**Filtrar en la app y confiar en ese filtro.** La consulta lleva `.eq("user_id", userId)` y no hay políticas. Se detecta quitando el filtro en una prueba: si aparecen notas ajenas, la seguridad dependía del cliente.
