## Objetivo

Al terminar esta lección podrás persistir la sesión de Supabase en SecureStore mediante un adaptador de `auth.storage`, sortear el límite de tamaño de SecureStore y controlar la renovación automática del access token según el estado de la app.

**Prerrequisitos:** `08-autenticacion-backend/04-storage`

## Concepto

Hasta ahora el cliente de Supabase usaba `persistSession: false`: cada vez que cierras la app, el usuario vuelve a escribir su contraseña. Nadie usa una app así. Pero guardar la sesión significa guardar en el teléfono dos credenciales valiosas, el access token y el refresh token, y el sitio donde las guardes decide quién puede leerlas.

### La analogía de la caja fuerte del hotel

Cuando te alojas en un hotel, puedes dejar el pasaporte encima de la mesa o dentro de la caja fuerte de la habitación. Ambos sitios están "en tu habitación", pero la mesa la ve cualquiera que entre a limpiar. AsyncStorage es la mesa: un archivo sin cifrar dentro del almacenamiento de la app. SecureStore es la caja fuerte: usa el Keychain en iOS y el Keystore en Android, que cifran los datos con claves protegidas por el sistema operativo.

### Access token y refresh token

Supabase entrega dos tokens al iniciar sesión:

- **Access token**: un JWT de vida corta (una hora por defecto) que acompaña cada petición a la base de datos o a Storage. RLS lee de él `auth.uid()`.
- **Refresh token**: una cadena opaca de vida larga que solo sirve para pedir un access token nuevo al servidor de autenticación.

Supabase aplica **rotación**: cada refresh token se puede usar una sola vez, y al usarlo recibes un par nuevo. Si alguien roba un refresh token y lo usa después que tú, el servidor detecta la reutilización y puede revocar la sesión. Por eso el refresh token es la credencial más valiosa del teléfono: quien lo tiene puede fabricar access tokens nuevos durante días.

<Callout kind="danger">
  Nunca guardes la sesión en AsyncStorage ni en MMKV sin cifrar. Ambos escriben texto plano en el sistema de archivos de la app: en un teléfono con root, en una copia de seguridad o con una herramienta de depuración, el refresh token se lee directamente y da acceso a la cuenta. El cliente de Supabase usa AsyncStorage si le pasas ese módulo como `storage`; pásale siempre un adaptador de SecureStore.
</Callout>

### El adaptador de `auth.storage`

El cliente de Supabase no sabe nada de SecureStore. Solo necesita un objeto con tres métodos asíncronos: `getItem`, `setItem` y `removeItem`. Cualquier cosa que cumpla esa forma sirve como almacén:

```ts
import * as SecureStore from "expo-secure-store";
import { createClient } from "@supabase/supabase-js";

const secureStoreAdapter = {
  getItem: (key: string) => SecureStore.getItemAsync(key),
  setItem: (key: string, value: string) => SecureStore.setItemAsync(key, value),
  removeItem: (key: string) => SecureStore.deleteItemAsync(key),
};

export const supabase = createClient(supabaseUrl, supabaseAnonKey, {
  auth: {
    storage: secureStoreAdapter,
    persistSession: true,
    autoRefreshToken: true,
    detectSessionInUrl: false,
    flowType: "pkce",
  },
});
```

`flowType: "pkce"` todavía no cambia nada en el inicio de sesión con email y contraseña, pero déjalo desde ahora: supabase-js solo usa PKCE si se lo pides, y el inicio de sesión con Google del proyecto de esta etapa lo necesita para canjear el código con `exchangeCodeForSession`. Sin esta opción, los tokens llegarían en el fragmento de la URL de retorno y el canje falla.

Con esto, al abrir la app el cliente lee la sesión guardada y emite el evento `INITIAL_SESSION` con ella, sin pedir la contraseña.

### El límite de tamaño y cómo sortearlo

La documentación de SecureStore advierte que algunas versiones de iOS rechazaban valores de más de unos 2048 bytes (https://docs.expo.dev/versions/latest/sdk/securestore/). La sesión de Supabase es un JSON con el access token, el refresh token y los datos del usuario, y puede superar ese tamaño. Hay dos soluciones documentadas:

1. **Trocear el valor** en fragmentos pequeños, cada uno con su propia clave (`key.0`, `key.1`...) y una clave extra con el número de fragmentos. Todo sigue dentro de SecureStore.
2. **Cifrar y separar**, como hace el `LargeSecureStore` del tutorial de Supabase para Expo (https://supabase.com/docs/guides/getting-started/tutorials/with-expo-react-native): se genera una clave AES aleatoria que se guarda en SecureStore, y la sesión cifrada con ella se guarda en AsyncStorage. En AsyncStorage solo queda texto cifrado inútil sin la clave.

En esta lección usas la primera, que no necesita librerías de cifrado:

```ts
const CHUNK_SIZE = 1800; // conservative: stays under 2048 bytes for ASCII values

async function removeChunks(key: string) {
  const count = Number(await SecureStore.getItemAsync(key + ".count")) || 0;
  for (let i = 0; i < count; i++) await SecureStore.deleteItemAsync(key + "." + i);
  await SecureStore.deleteItemAsync(key + ".count");
}

export const chunkedSecureStore = {
  async getItem(key: string) {
    const count = Number(await SecureStore.getItemAsync(key + ".count"));
    if (!count) return null;
    let value = "";
    for (let i = 0; i < count; i++) {
      const part = await SecureStore.getItemAsync(key + "." + i);
      if (part === null) return null; // incomplete: treat as signed out
      value += part;
    }
    return value;
  },
  async setItem(key: string, value: string) {
    await removeChunks(key);
    const count = Math.ceil(value.length / CHUNK_SIZE);
    for (let i = 0; i < count; i++) {
      await SecureStore.setItemAsync(key + "." + i, value.slice(i * CHUNK_SIZE, (i + 1) * CHUNK_SIZE));
    }
    await SecureStore.setItemAsync(key + ".count", String(count));
  },
  removeItem: removeChunks,
};
```

Las claves de SecureStore solo admiten letras, números, `.`, `-` y `_`; la clave que usa Supabase (`sb-<ref>-auth-token`) cumple esa regla, y los sufijos `.0` o `.count` también.

### Renovar solo en primer plano

`autoRefreshToken: true` programa la renovación antes de que caduque el access token. En React Native, los temporizadores no son fiables cuando la app está en segundo plano, así que Supabase recomienda encender y apagar la renovación según el estado de la app con `AppState`:

```ts
import { AppState } from "react-native";

AppState.addEventListener("change", (state) => {
  if (state === "active") supabase.auth.startAutoRefresh();
  else supabase.auth.stopAutoRefresh();
});
```

Al volver a primer plano, `startAutoRefresh` comprueba el token y lo renueva de inmediato si ya caducó.

### Cerrar sesión de verdad

`supabase.auth.signOut()` hace dos cosas: revoca el refresh token en el servidor y llama a `removeItem` en tu adaptador. Si solo borras SecureStore a mano, el refresh token sigue siendo válido en el servidor hasta que caduque.

## Errores comunes

**Dejar AsyncStorage como almacén de la sesión.** Se ve como `auth: { storage: AsyncStorage }`, copiado de un ejemplo antiguo. Ocurre porque funciona igual y no da errores. Se detecta buscando `storage:` en la configuración de `createClient` o inspeccionando el almacenamiento de la app en un emulador: si aparece un JSON con `refresh_token` legible, la sesión está en texto plano.

**Superar el límite de SecureStore sin trocear.** La sesión se guarda en algunos dispositivos y en otros no, y el usuario "pierde" la sesión al reiniciar la app sin ningún mensaje claro. Ocurre porque el JSON de sesión crece con los metadatos del usuario. Se detecta registrando `value.length` en `setItem` durante el desarrollo y capturando los errores de `setItemAsync`.

**No parar la renovación en segundo plano.** Tras dejar la app minimizada un rato, las peticiones fallan con 401 al volver, o aparecen avisos de temporizadores largos. Ocurre porque los temporizadores de JavaScript se congelan en segundo plano. Se detecta dejando la app en segundo plano más de una hora y volviendo: con el listener de `AppState` el token se renueva al activarse.

**Borrar el almacén en lugar de llamar a `signOut`.** La app parece cerrar sesión, pero el refresh token sigue vivo en el servidor. Se detecta en **Authentication, Users** del panel, donde la sesión sigue apareciendo activa.
