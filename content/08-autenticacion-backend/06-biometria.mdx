## Objetivo

Al terminar esta lección podrás bloquear la app cuando vuelve del segundo plano, pedir huella o Face ID con `expo-local-authentication` para desbloquearla y explicar qué protege la biometría y qué no.

**Prerrequisitos:** `08-autenticacion-backend/05-securestore-y-refresh-tokens`

## Concepto

Con la sesión guardada en SecureStore, el usuario ya no escribe la contraseña cada vez que abre la app. Es cómodo, pero abre otro riesgo: quien tome el teléfono desbloqueado puede abrir la app de notas y leerlo todo. La biometría añade una comprobación local rápida: "¿sigue siendo el dueño quien tiene el teléfono en la mano?".

### La analogía de la puerta de casa

Tu casa tiene cerradura con llave, pero dentro también puedes tener un cajón con candado para los documentos importantes. La llave de casa (la sesión) demuestra que vives ahí. El candado del cajón (la biometría) evita que un invitado que ya está dentro abra ese cajón concreto. El candado no sustituye a la puerta: si alguien tiene tu llave, puede entrar igual por otra vía.

### Qué protege y qué no

La biometría en una app móvil es una **comprobación local**:

- El sistema operativo compara la huella o la cara con las registradas en el dispositivo y responde solo "sí" o "no". Tu app nunca recibe la huella ni la imagen de la cara.
- El servidor de Supabase no se entera de nada: no es una autenticación contra el backend, sino una puerta delante de una sesión que ya existe.
- Protege frente a alguien que usa el teléfono desbloqueado. No protege frente a un atacante que ya extrajo el refresh token, porque ese atacante no usa tu app.

Hay un límite más. Si el bloqueo solo depende de que `authenticateAsync` devuelva `success: true` y tu código llame a `setLocked(false)`, ningún secreto depende del resultado biométrico: en un dispositivo con root o jailbreak, un atacante con herramientas de instrumentación puede forzar esa rama y saltarse el diálogo. Es un control de experiencia de usuario y de defensa en profundidad, no una garantía en dispositivos comprometidos (OWASP lo trata en MASVS-AUTH-2: https://mas.owasp.org/MASVS/controls/MASVS-AUTH-2/).

Si necesitas más, puedes atar el secreto a la biometría: `SecureStore.setItemAsync(key, value, { requireAuthentication: true })` guarda el valor de forma que el sistema operativo exige huella o cara para leerlo (https://docs.expo.dev/versions/latest/sdk/securestore/). El costo: en iOS necesitas `NSFaceIDUsageDescription`, el usuario debe tener una biometría registrada, la lectura falla en dispositivos sin ella y, si el usuario cambia sus huellas, el valor queda inaccesible y hay que volver a iniciar sesión. Para la app de notas, el bloqueo de interfaz es suficiente; para datos más sensibles, evalúa atar la sesión.

Por eso la biometría se suma a lo que ya tienes (sesión en SecureStore, RLS en el servidor), nunca lo reemplaza.

### La API de `expo-local-authentication`

Instálala con `npx expo install expo-local-authentication`. Antes de pedir la biometría, comprueba que el dispositivo puede usarla:

```ts
import * as LocalAuthentication from "expo-local-authentication";

async function canUseBiometrics(): Promise<boolean> {
  const hasHardware = await LocalAuthentication.hasHardwareAsync();
  const isEnrolled = await LocalAuthentication.isEnrolledAsync();
  return hasHardware && isEnrolled;
}

async function unlock(): Promise<boolean> {
  const result = await LocalAuthentication.authenticateAsync({
    promptMessage: "Desbloquea tus notas",
    cancelLabel: "Cancelar",
    disableDeviceFallback: false, // allow the device passcode if biometrics fail
  });
  return result.success;
}
```

- `hasHardwareAsync` indica si hay sensor; `isEnrolledAsync`, si el usuario registró al menos una huella o cara.
- `authenticateAsync` muestra el diálogo del sistema y devuelve `{ success: true }` o `{ success: false, error }`, donde `error` explica el motivo (por ejemplo `user_cancel` o `lockout`).
- Con `disableDeviceFallback: false` el sistema ofrece el código del dispositivo si la biometría falla varias veces. Es la opción recomendada: una huella dañada no debe dejar al usuario fuera de sus datos.

En iOS, Face ID necesita un texto que explique su uso. Con el config plugin se declara en `app.json`:

```json
{
  "expo": {
    "plugins": [
      ["expo-local-authentication", { "faceIDPermission": "Usamos Face ID para desbloquear tus notas." }]
    ]
  }
}
```

La documentación oficial advierte que Face ID no funciona en Expo Go: para probarlo necesitas un development build. La huella en Android sí funciona en Expo Go. Referencia completa: https://docs.expo.dev/versions/latest/sdk/local-authentication/.

### Bloquear al volver del segundo plano

`AppState` informa de los cambios de estado de la app: `active`, `background` e `inactive` (este último solo en iOS, durante transiciones breves). La estrategia es:

1. Al pasar a `background`, guarda la hora.
2. Al volver a `active`, si pasó más tiempo que el margen elegido (por ejemplo 30 segundos), muestra la pantalla de bloqueo y pide la biometría.

```ts
const lastBackgroundAt = useRef<number | null>(null);

useEffect(() => {
  const subscription = AppState.addEventListener("change", (state) => {
    if (state === "background") lastBackgroundAt.current = Date.now();
    if (state === "active" && lastBackgroundAt.current !== null) {
      if (Date.now() - lastBackgroundAt.current > LOCK_AFTER_MS) setLocked(true);
      lastBackgroundAt.current = null;
    }
  });
  return () => subscription.remove();
}, []);
```

Un detalle importante: el propio diálogo de Face ID hace que iOS pase la app a `inactive` y luego a `active`. Si bloquearas en `inactive`, cada desbloqueo provocaría un bloqueo nuevo, en un bucle infinito. Por eso la hora se guarda solo en `background`.

Mientras la app está bloqueada, no renderices las notas debajo de la pantalla de bloqueo: devuelve solo la pantalla de bloqueo. Así los datos no aparecen ni un instante.

      </Pressable>

## Errores comunes

**Bloquear en `inactive`.** La app pide Face ID, el usuario se autentica y aparece otra vez la pantalla de bloqueo, sin fin. Ocurre porque el diálogo del sistema pasa la app a `inactive` y de vuelta a `active`. Se detecta registrando cada cambio de `AppState` en consola: si ves `inactive` justo después de pedir la biometría, el bloqueo debe depender solo de `background`.

**Tratar la biometría como autenticación contra el servidor.** El código borra la sesión y "vuelve a iniciar sesión" con la huella, o envía `success: true` a la API como prueba. Ocurre por confundir comprobación local con identidad. Se detecta revisando qué ocurre tras `authenticateAsync`: solo debe cambiar un estado local de la app; la identidad ante Supabase sigue siendo el token.

**Dejar al usuario sin salida.** Con `disableDeviceFallback: true` y un sensor que falla, el usuario no puede entrar nunca. Se detecta probando en un dispositivo sin huellas registradas o cancelando varias veces el diálogo. Ofrece siempre el código del dispositivo o, como último recurso, cerrar sesión y volver a entrar con la contraseña.

**Probar Face ID en Expo Go.** El diálogo no aparece o falla en iOS. Ocurre porque Expo Go no incluye el permiso de Face ID. Se detecta porque funciona en Android pero no en iPhone; crea un development build con el config plugin.
