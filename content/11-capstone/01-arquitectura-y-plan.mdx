## Objetivo

Al terminar esta lección podrás organizar tu app en carpetas por feature con las capas domain, application, infrastructure y ui, documentar su modelo de amenazas y su clasificación de datos, y planificar el trabajo en entregas verticales.

**Prerrequisitos:** `11-capstone/00-elegir-y-definir-tu-app`, `05-estado-datos-arquitectura/10-proyecto-app-con-api`, `09-seguridad-movil/09-proyecto-auditoria`

## Concepto

En la lección anterior escribiste qué va a hacer tu app. Ahora decides cómo se organiza el código, qué puede salir mal y en qué orden lo construyes. No hay herramientas nuevas: aplicas lo que aprendiste en [Arquitectura hexagonal](/etapa/05-estado-datos-arquitectura/06-arquitectura-hexagonal), [Screaming architecture](/etapa/05-estado-datos-arquitectura/07-screaming-architecture), [Atomic design](/etapa/05-estado-datos-arquitectura/08-atomic-design) y [Modelo de amenazas móvil](/etapa/09-seguridad-movil/00-modelo-de-amenazas-movil).

### La cocina de un restaurante

En la cocina de un restaurante cada estación tiene su tarea: una prepara ensaladas, otra la parrilla, otra los postres. Dentro de cada estación hay un orden fijo: la receta (qué lleva el plato), el procedimiento (en qué orden se hace), los proveedores (de dónde vienen los ingredientes) y el emplatado (cómo llega a la mesa). Si cambias de proveedor de tomates, la receta no cambia.

Tu app funciona igual. Cada **feature** es una estación, y dentro de ella las cuatro capas cumplen los cuatro roles:

| Capa | Rol en la cocina | Qué contiene | Puede importar |
| --- | --- | --- | --- |
| `domain` | La receta | Tipos, reglas puras, puertos (interfaces) | Nada externo |
| `application` | El procedimiento | Casos de uso que orquestan el dominio a través de puertos | `domain` |
| `infrastructure` | Los proveedores | Adaptadores: Supabase, SQLite, SecureStore, notificaciones | `domain`, librerías |
| `ui` | El emplatado | Pantallas, componentes y hooks de React | `application`, `domain` |

La regla que no se negocia: **las dependencias apuntan hacia adentro**. El dominio no importa React, React Native, Expo ni Supabase. Así puedes probarlo con pruebas unitarias rápidas y cambiar de proveedor sin tocar las reglas.

### El árbol de carpetas

Con el registro de hábitos como ejemplo, el árbol queda así:

```text
app/                         # Expo Router routes, thin: they only render screens
  (tabs)/index.tsx
  habit/[id].tsx
src/
  features/
    habits/
      domain/                # Habit, currentStreak, HabitRepository port
      application/           # completeHabit, createHabit use cases
      infrastructure/        # SupabaseHabitRepository, InMemoryHabitRepository
      ui/                    # HabitListScreen, useHabits hook
    reminders/
      domain/ application/ infrastructure/ ui/
    auth/
      domain/ application/ infrastructure/ ui/
  shared/
    ui/atoms/ ui/molecules/ ui/organisms/
    infrastructure/          # supabase client, secure storage adapter
```

Las carpetas de primer nivel dentro de `features` gritan qué hace la app: hábitos, recordatorios, autenticación. Los componentes reutilizables viven en `shared/ui` organizados con atomic design, y cada feature arma sus pantallas con ellos.

Un detalle práctico: los archivos de `app/` deben ser delgados. Una ruta solo importa la pantalla de la feature y la renderiza. Si una ruta empieza a tener lógica, esa lógica pertenece a `application` o a un hook en `ui`.

### Modelo de amenazas en media página

Antes de escribir código, recorre tu app con las preguntas de STRIDE-lite que usaste en la etapa 9. No necesitas un documento largo: una tabla con amenaza, activo afectado y mitigación basta.

```text
Asset: user's habits and reminder times (per-user data in Supabase)
- Spoofing: someone uses a stolen session -> tokens in SecureStore, short-lived access token
- Tampering: user edits another user's habit -> RLS policy with auth.uid() on every table
- Information disclosure: crash report includes the email -> Sentry beforeSend scrubbing
- Denial of service: notification spam -> one scheduled reminder per habit
- Elevation of privilege: service key in the bundle -> only the anon key ships, no secrets
```

### Clasificación de datos

Clasifica cada dato que tu app toca y decide dónde vive, como hiciste en [Almacenamiento seguro](/etapa/09-seguridad-movil/03-almacenamiento-seguro):

| Dato | Clase | Dónde vive |
| --- | --- | --- |
| Nombre del hábito, fechas completadas | Personal | Supabase con RLS, caché en SQLite |
| Token de sesión y refresh token | Sensible | SecureStore |
| Preferencia de tema | Pública | AsyncStorage |
| Correo del usuario | Personal | Supabase Auth; nunca en logs ni reportes de errores |

Esta tabla alimenta después las etiquetas de privacidad de las tiendas, así que conviene escribirla ahora.

### Plan de trabajo en rebanadas verticales

Un pastel se corta de arriba abajo: cada porción lleva todas las capas. Planifica igual. En lugar de "semana 1: todo el dominio, semana 2: toda la UI", cada entrega atraviesa las cuatro capas de una historia de usuario y termina funcionando en el teléfono:

1. Esqueleto: proyecto Expo, TypeScript strict, ESLint, CI con lint y typecheck, carpetas vacías.
2. Historia 1 de punta a punta con un repositorio en memoria y sus pruebas unitarias.
3. Autenticación y el repositorio de Supabase con RLS reemplazando al de memoria.
4. Historias 2 y 3, la función nativa y el flujo E2E de Maestro.
5. Seguridad y release: autoauditoría MASVS, perfiles de EAS, Sentry, publicación.

Cada rebanada tiene su propia definición de terminado: pruebas en verde, CI en verde y la función visible en un development build. La documentación de Expo sobre la estructura de un proyecto está en https://docs.expo.dev/get-started/start-developing/.

## Ejercicio

<Challenge
  title="Puerto, adaptador y caso de uso"
  solution={
    <Playground
      lang="ts"
      code={`interface Habit {
  id: string;
  name: string;
  completedOn: string[];
}

// Port: lives in domain
interface HabitRepository {
  findById(id: string): Promise<Habit | undefined>;
  save(habit: Habit): Promise<void>;
}

// Adapter: lives in infrastructure
class InMemoryHabitRepository implements HabitRepository {
  private items = new Map<string, Habit>();

  async findById(id: string): Promise<Habit | undefined> {
    return this.items.get(id);
  }

  async save(habit: Habit): Promise<void> {
    this.items.set(habit.id, habit);
  }
}

// Use case: lives in application
function makeCompleteHabit(repository: HabitRepository) {
  return async (id: string, day: string): Promise<Habit> => {
    const habit = await repository.findById(id);
    if (!habit) throw new Error("Habit not found: " + id);
    if (habit.completedOn.includes(day)) return habit;
    const updated = { ...habit, completedOn: [...habit.completedOn, day] };
    await repository.save(updated);
    return updated;
  };
}

async function main(): Promise<void> {
  const repository = new InMemoryHabitRepository();
  await repository.save({ id: "h1", name: "Read 10 pages", completedOn: [] });
  const completeHabit = makeCompleteHabit(repository);

  const first = await completeHabit("h1", "2026-09-26");
  const second = await completeHabit("h1", "2026-09-26");
  console.log(first.completedOn.length); // 1
  console.log(second.completedOn.length); // 1

  try {
    await completeHabit("missing", "2026-09-26");
  } catch (error) {
    console.log((error as Error).message); // Habit not found: missing
  }
}

main();`}
    />
  }
>
  Escribe en TypeScript las tres piezas de la historia 1 del registro de hábitos: el puerto `HabitRepository` (con `findById` y `save`), un adaptador `InMemoryHabitRepository` y un caso de uso `makeCompleteHabit(repository)` que marca un hábito como hecho en una fecha. El caso de uso debe cumplir el criterio de aceptación "marcarlo dos veces el mismo día no cuenta doble" y lanzar un error si el hábito no existe. Si tu app es otra, escribe el puerto y el caso de uso de tu historia 1.

## Errores comunes

**El dominio importa librerías de infraestructura.** Se ve como `import { supabase } from "../../shared/infrastructure/supabase"` dentro de `domain/` o `application/`. Ocurre porque llamar directamente a Supabase parece más corto que definir un puerto. Se detecta buscando imports prohibidos en las capas internas, por ejemplo con `grep -rE "from ['\"](react|react-native|expo|@supabase)" src/features/*/domain src/features/*/application`; cualquier resultado es una violación.

**Carpetas por tipo en lugar de por feature.** Se ve como `src/screens`, `src/hooks`, `src/services` con archivos de todas las features mezclados. Ocurre por costumbre de proyectos pequeños. Se detecta cuando un cambio en una historia obliga a tocar archivos en cuatro carpetas lejanas; con carpetas por feature, el cambio queda dentro de una sola.

**Planificar por capas horizontales.** Se ve como un plan que dedica semanas enteras al dominio sin nada visible en el teléfono. Ocurre porque parece ordenado terminar una capa antes de la siguiente. Se detecta cuando al final de una entrega no puedes mostrar ninguna historia funcionando; reorganiza el plan para que cada entrega cruce las cuatro capas.
