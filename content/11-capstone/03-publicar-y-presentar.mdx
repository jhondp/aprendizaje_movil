## Objetivo

Al terminar esta lección podrás llevar tu app a las pruebas internas de ambas tiendas, documentarla con un README que otra persona entienda y presentarla en una demo de 5 minutos.

**Prerrequisitos:** `11-capstone/02-rubrica-y-checklist-final`, `10-build-release-operaciones/11-proyecto-publicar`

## Concepto

Una app que nadie puede instalar ni entender no está terminada, aunque su código sea excelente. Esta última lección cubre tres entregas: la publicación, el README y la presentación. La publicación repite el runbook de [Proyecto: publicar la app en ambas tiendas](/etapa/10-build-release-operaciones/11-proyecto-publicar), ahora con tu propia app.

### La inauguración de una exposición

Un pintor puede pasar meses en su taller, pero la exposición se juzga el día de la inauguración. Ese día importan tres cosas: que los cuadros estén colgados (la app instalable), que cada uno tenga su ficha con título, técnica y año (el README y la pantalla Acerca de) y que el artista pueda contar en pocos minutos qué buscaba (la demo). Si falta cualquiera de las tres, el público se va sin entender la obra.

### Publicar: el runbook resumido

Ya hiciste este recorrido en la etapa 10. Para tu app, el orden es:

```bash
# 1. Production builds for both platforms
eas build --profile production --platform all

# 2. Send them to TestFlight and to Play internal testing
eas submit --platform ios --latest
eas submit --platform android --latest

# 3. Ship one OTA update to prove the update channel works
eas update --branch production --message "fix: copy on the empty state"
```

Antes de enviar, confirma lo que las tiendas revisan con más frecuencia: la URL de la política de privacidad, las etiquetas de privacidad que coinciden con tu clasificación de datos, textos de permisos que explican para qué se usa cada uno y una cuenta de prueba si la app requiere inicio de sesión. Los detalles están en [Ficha de la tienda y proceso de revisión](/etapa/10-build-release-operaciones/06-store-listing-y-revision) y en la documentación de EAS Submit: https://docs.expo.dev/submit/introduction/.

### La pantalla Acerca de

Una pantalla Acerca de es la ficha del cuadro dentro de la app. Muestra el nombre, la versión y el número de build (lo primero que te pedirá alguien que reporta un error), la descripción en una frase, enlaces a la política de privacidad, al código fuente y a las licencias de terceros, y un contacto. La política de privacidad dentro de la app no es un adorno: las tiendas piden que sea accesible para el usuario.

En tu app real, la versión no se escribe a mano: se lee de la configuración con `expo-constants` o `expo-application`, para que siempre coincida con la build instalada. En la práctica de abajo va como constante para que el ejemplo no dependa de paquetes externos.

### El README

El README es lo primero que ve cualquiera que abra tu repositorio. GitHub lo muestra en la portada del proyecto y explica su propósito en https://docs.github.com/es/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes. Una estructura que funciona:

```markdown
# Habit Tracker

Mark a daily habit in one tap and keep your streak visible.

![Home screen](docs/screenshots/home.png) ![Habit detail](docs/screenshots/detail.png)

## Problem
People who want to build a habit forget it after the first week.

## Features
- Mark today's habit, see the current streak, daily reminder.

## Architecture
Feature folders (habits, reminders, auth) with domain, application,
infrastructure and ui layers. See docs/threat-model.md and docs/rubric.md.

## Run it locally
pnpm install
cp .env.example .env   # fill EXPO_PUBLIC_SUPABASE_URL and EXPO_PUBLIC_SUPABASE_ANON_KEY
npx expo start

## Quality
[![CI](https://github.com/your-user/habit-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/your-user/habit-tracker/actions)
```

Las capturas van en `docs/screenshots/` y se toman de un dispositivo o simulador real, con datos de ejemplo, nunca con datos personales. Si tus capturas de la ficha de la tienda ya existen, reutilízalas.

### El guion de demo de 5 minutos

Una demo sin guion termina en diez minutos de navegar pantallas al azar. Escribe el guion y ensáyalo con cronómetro:

| Minuto | Contenido |
| --- | --- |
| 0:00 a 0:45 | El problema en una frase y para quién es la app |
| 0:45 a 2:30 | Las tres historias de usuario en vivo, en un teléfono con la build de TestFlight o de Play |
| 2:30 a 3:30 | La arquitectura: el árbol de carpetas y una regla de dominio con su prueba |
| 3:30 a 4:30 | Calidad y seguridad: CI en verde, RLS con un segundo usuario, evento de Sentry sin datos personales |
| 4:30 a 5:00 | Qué aprendiste y qué sigue (tu lista de fuera de alcance es la versión 1.1) |

Prepara un plan B: si la red falla, muestra una grabación de pantalla de las historias. Una demo en vivo que se cae consume los 5 minutos.

function describe(message: string): string {
  const separator = message.indexOf(": ");
  const header = message.slice(0, separator);
  const text = message.slice(separator + 2);
  const open = header.indexOf("(");
  const scope = open === -1 ? "" : header.slice(open + 1, header.indexOf(")")) + ": ";
  return "- " + scope + text;
}

function buildChangelog(version: string, date: string, messages: string[]): string[] {
  const added = messages.filter((m) => m.startsWith("feat")).map(describe);
  const fixed = messages.filter((m) => m.startsWith("fix")).map(describe);
  const lines = ["## " + version + " - " + date];
  if (added.length > 0) lines.push("### Added", ...added);
  if (fixed.length > 0) lines.push("### Fixed", ...fixed);
  return lines;
}

## Errores comunes

**Enviar a revisión sin cuenta de prueba.** Se ve como un rechazo de la revisión de Apple o de Google porque el revisor no pudo pasar la pantalla de inicio de sesión. Ocurre porque tú siempre entras con tu cuenta y olvidas que el revisor no tiene una. Se detecta leyendo el motivo del rechazo en App Store Connect o en Play Console; se evita creando una cuenta de prueba con datos de ejemplo y escribiéndola en las notas de revisión.

**Capturas con datos personales o de desarrollo.** Se ve como capturas del README o de la tienda que muestran tu correo real, nombres de amigos o textos como "test test". Ocurre porque se toman en el mismo dispositivo donde desarrollas. Se detecta revisando cada captura antes de subirla; se evita con un usuario de demostración y datos de ejemplo creíbles.

**Una demo que recorre pantallas en lugar de historias.** Se ve como "esta es la pantalla de inicio, esta es la de ajustes, esta es la de perfil", sin explicar para qué sirve cada una. Ocurre porque se improvisa. Se detecta ensayando con cronómetro: si a los 3 minutos todavía no mostraste la historia 1 funcionando, reordena el guion alrededor de las historias.
