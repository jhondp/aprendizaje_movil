## Objetivo

Al terminar esta lección podrás configurar `expo-updates`, publicar una actualización OTA en el canal de producción con `eas update`, explicar qué puede y qué no puede cambiar una actualización, y revertirla con `eas update:rollback`.

**Prerrequisitos:** `10-build-release-operaciones/06-store-listing-y-revision`

## Concepto

Acabas de ver que llegar a la tienda implica build, envío y revisión: días, no minutos. Si mañana descubres un error de texto o un bug en una pantalla, repetir todo el ciclo por un cambio de tres líneas es desproporcionado. **EAS Update** permite enviar a las apps ya instaladas una nueva versión del JavaScript y los assets sin pasar por la tienda. Es lo que se conoce como actualización **over the air** (OTA).

Piensa en una consola de videojuegos. El aparato físico se compra una vez en la tienda; los juegos y sus parches se descargan cuando se enciende. Nadie vuelve a la tienda por un parche. Pero un parche no convierte una consola vieja en una nueva: si el juego necesita un chip que la consola no tiene, hay que comprar otra consola. En tu app, el "aparato" es la parte nativa que compilaste con EAS Build; el "parche" es el bundle de JavaScript.

### Qué puede cambiar una actualización y qué no

Esta es la línea que separa un despliegue correcto de una app rota:

| Puede cambiar por OTA                                   | Requiere un build nuevo y pasar por la tienda                    |
| ------------------------------------------------------- | ---------------------------------------------------------------- |
| Cualquier archivo `.ts` / `.tsx` de tu código           | Instalar o actualizar una dependencia con código nativo          |
| Imágenes y fuentes que importas desde JavaScript        | Icono, splash, nombre, `bundleIdentifier`, `package`             |
| Textos, estilos, lógica, pantallas, navegación          | Permisos, `infoPlist`, `plugins` y cualquier campo nativo de `app.config.ts` |
| Valores `EXPO_PUBLIC_` incrustados en el bundle         | La versión del SDK de Expo o de React Native                     |

La regla práctica: si el cambio tocó `package.json` con una librería nativa o cualquier campo de `app.config.ts` que no sea `extra`, no lo publiques por OTA.

### runtimeVersion: el guardián

¿Cómo sabe la app si una actualización es compatible con su parte nativa? Por la **runtime version**. Cada build lleva una etiqueta de runtime; cada actualización se publica para una runtime concreta; una app solo descarga actualizaciones cuya runtime coincida con la suya. Si publicas una actualización que usa una librería nativa nueva pero la runtime no cambió, la app la descarga y falla al arrancar. La lección de versionado explica las políticas para elegir esa etiqueta; por ahora usarás la más simple, que iguala la runtime a `version`.

### Configurar el proyecto

Instala `expo-updates` y ejecuta la configuración. Con `app.config.ts`, la CLI no puede editar el archivo por ti: te muestra los campos que debes agregar (https://docs.expo.dev/eas-update/getting-started/).

```sh
npx expo install expo-updates
eas update:configure
```

Los campos en `app.config.ts`:

```ts
export default ({ config }: ConfigContext): ExpoConfig => ({
  ...config,
  // ...name, slug, ios, android as before
  updates: {
    url: "https://u.expo.dev/<projectId>",
  },
  runtimeVersion: {
    policy: "appVersion",
  },
});
```

`<projectId>` es el identificador de tu proyecto en EAS (lo ves en `eas project:info`). Y recuerda el campo `channel` que cada perfil de `eas.json` ya declara: un build del perfil `production` escucha el canal `production`; uno de `preview`, el canal `preview`. Las actualizaciones se publican en **ramas** (branches) y cada canal apunta a una rama; por defecto, `eas update` crea una rama con el mismo nombre que el canal y las enlaza, así que en el uso diario puedes pensar "canal = rama".

Como agregaste una dependencia nativa (`expo-updates`) y campos nativos en la configuración, necesitas un build nuevo antes de que nada de esto funcione. Ese build será el primero capaz de recibir actualizaciones.

### Publicar

```sh
eas update --channel production --message "Fix note title truncation"
```

La CLI exporta el bundle, sube los assets y crea una actualización en la rama enlazada al canal. Las apps de producción con esa runtime la descargan la próxima vez que arrancan: por defecto, `expo-updates` comprueba al inicio, descarga en segundo plano y aplica la actualización **en el siguiente arranque**, para no interrumpir al usuario. Puedes verificar el estado del canal con `eas channel:view production` y listar actualizaciones con `eas update:list --branch production`.

<Callout kind="tip">
  Publica siempre primero en el canal `preview` y abre la app de preview en un teléfono real. Solo cuando la actualización se aplica y la app arranca bien, publica en `production` con el mismo commit.
</Callout>

### Rollback

Algo salió mal en producción. Tienes dos maneras de volver atrás, y ambas se publican como una actualización más (la app no "desinstala" nada: descarga la versión anterior como si fuera nueva). Documentación: https://docs.expo.dev/eas-update/rollbacks/.

```sh
eas update:rollback
```

El comando pregunta a qué canal aplica y ofrece dos opciones:

- **Rollback a la actualización anterior**: republica una actualización previa de la rama. Es lo habitual cuando la penúltima estaba bien.
- **Rollback al embedded update**: indica a las apps que vuelvan al bundle que traían compilado desde el build. Útil cuando ninguna actualización publicada es de confianza.

En ambos casos, los usuarios reciben el rollback con la misma mecánica: al siguiente arranque. Un rollback OTA tarda minutos en llegar; un rollback de tienda tarda días. Esa asimetría es la razón principal para separar cambios JS de cambios nativos.

### Actualizar sin esperar al siguiente arranque

Si necesitas que el usuario reciba un cambio de inmediato (por ejemplo, un arreglo de seguridad), la API de `expo-updates` permite comprobar, descargar y recargar desde el código:

```ts
import * as Updates from "expo-updates";

export async function applyUpdateNow(): Promise<void> {
  const check = await Updates.checkForUpdateAsync();
  if (!check.isAvailable) return;
  await Updates.fetchUpdateAsync();
  await Updates.reloadAsync();
}
```

Úsalo con criterio: recargar la app sin avisar en mitad de una tarea es una mala experiencia. Un patrón razonable es mostrar un aviso y dejar que el usuario pulse "Actualizar".

## Errores comunes

**Publicar por OTA un cambio que agregó una librería nativa.** La actualización se descarga, la app arranca con el JS nuevo, intenta llamar al módulo nativo que no existe y se cierra. Ocurre porque `eas update` no verifica tus dependencias nativas. Se detecta porque el crash aparece justo después de la actualización y solo en producción. Solución inmediata: `eas update:rollback`; después, subir la versión, construir y publicar en la tienda.

**Esperar que la actualización se vea al instante.** Publicas, abres la app y sigue igual. Ocurre porque `expo-updates` descarga en segundo plano y aplica en el siguiente arranque. Se detecta porque al cerrar y volver a abrir la app aparece el cambio. No es un error; si necesitas inmediatez, usa la API de `expo-updates` con un aviso al usuario.

**Publicar en el canal equivocado.** Los testers de preview ven el cambio y los usuarios no, o al revés. Ocurre porque `--channel` es un parámetro libre. Se detecta con `eas channel:view <canal>`, que muestra la última actualización publicada. Escribe el canal como parte de un script (`"update:prod": "eas update --channel production"`) para no teclearlo a mano.
