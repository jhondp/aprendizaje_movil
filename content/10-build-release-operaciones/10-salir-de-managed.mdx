## Objetivo

Al terminar esta lección podrás explicar qué genera `npx expo prebuild` y por qué EAS Build lo ejecuta por ti, escribir un config plugin mínimo que modifique la configuración nativa, y decidir con criterio cuándo necesitas un módulo nativo local en lugar de salir del workflow managed.

**Prerrequisitos:** `10-build-release-operaciones/09-monitoreo-sentry`

## Concepto

Durante todo el curso trabajaste sin carpetas `ios/` ni `android/` en el repositorio. Eso es el **workflow managed**: Expo genera los proyectos nativos cuando hacen falta y tú solo mantienes `app.config.ts`, `package.json` y tu código. Tarde o temprano aparece un requisito que la configuración no cubre: una entrada en `AndroidManifest.xml` que ninguna librería expone, una clave en `Info.plist`, un SDK de terceros sin soporte para Expo. La reacción clásica era "eyectar" a React Native puro y perder el tooling. Hoy hay un camino intermedio que conviene entender bien.

Piensa en una casa prefabricada. La fábrica produce la estructura a partir de tus planos (`app.config.ts`); si quieres un enchufe extra, no compras un terreno y construyes desde cero: cambias los planos y la fábrica vuelve a producirla. Y si la fábrica no ofrece ese enchufe, le entregas una instrucción de montaje (un config plugin) para que lo instale en cada producción. Solo si necesitas algo que ninguna fábrica hará, te planteas construir a mano.

### Qué hace prebuild

`npx expo prebuild` toma `app.config.ts` y las dependencias con código nativo y genera las carpetas `ios/` y `android/` completas: proyecto de Xcode, Gradle, manifest, plist, iconos y splash (https://docs.expo.dev/workflow/prebuild/). Es exactamente lo que EAS Build hace en el servidor al principio de cada build cuando esas carpetas no existen en el repositorio. Por eso nunca las viste: el proceso se llama **Continuous Native Generation** (CNG) y significa que las carpetas nativas son un artefacto generado, no código fuente.

Puedes ejecutarlo en tu máquina para inspeccionar el resultado o para compilar localmente con `npx expo run:android` o `npx expo run:ios` (este último requiere macOS y Xcode). La opción `--clean` borra y regenera las carpetas, lo que garantiza que reflejan la configuración actual.

<Callout kind="warning">
  Si haces commit de `ios/` y `android/` y luego los editas a mano, esos cambios se pierden en el siguiente `prebuild --clean` y EAS Build dejará de regenerarlos (usa los tuyos). Es una decisión legítima, pero explícita: a partir de ahí tú mantienes los proyectos nativos. Mientras las carpetas estén en `.gitignore`, sigues en managed.
</Callout>

### Config plugins: modificar lo nativo desde JavaScript

Un **config plugin** es una función que recibe la configuración de Expo y devuelve una configuración modificada, con instrucciones sobre qué tocar en los proyectos nativos cuando se ejecute prebuild (https://docs.expo.dev/config-plugins/introduction/). Las librerías con código nativo traen el suyo (`expo-camera`, `@sentry/react-native/expo`...). Tú puedes escribir uno local cuando necesitas un cambio que ninguna librería expone.

Este plugin agrega un permiso a `AndroidManifest.xml` y una clave a `Info.plist`:

```js
// plugins/withNotesPlatformConfig.js
const { withAndroidManifest, withInfoPlist } = require("expo/config-plugins");

function addAndroidPermission(config, permission) {
  return withAndroidManifest(config, (mod) => {
    const manifest = mod.modResults.manifest;
    manifest["uses-permission"] = manifest["uses-permission"] ?? [];
    const exists = manifest["uses-permission"].some((p) => p.$["android:name"] === permission);
    if (!exists) {
      manifest["uses-permission"].push({ $: { "android:name": permission } });
    }
    return mod;
  });
}

function addInfoPlistKey(config, key, value) {
  return withInfoPlist(config, (mod) => {
    mod.modResults[key] = value;
    return mod;
  });
}

module.exports = function withNotesPlatformConfig(config) {
  config = addAndroidPermission(config, "android.permission.VIBRATE");
  config = addInfoPlistKey(config, "ITSAppUsesNonExemptEncryption", false);
  return config;
};
```

Y se registra en `app.config.ts`:

```ts
plugins: [
  "expo-router",
  "./plugins/withNotesPlatformConfig",
],
```

Dos detalles importan. El plugin se ejecuta en cada prebuild, así que debe ser **idempotente**: comprobar si el permiso ya existe antes de agregarlo evita duplicados. Y la clave `ITSAppUsesNonExemptEncryption` es un ejemplo útil: es la declaración de cifrado que App Store Connect pregunta en cada envío; ponerla en `false` (cuando la app solo usa HTTPS estándar) evita el formulario manual. Expo también expone ese caso como `ios.config.usesNonExemptEncryption`, lo que ilustra la regla: **antes de escribir un plugin, busca si la configuración ya tiene un campo para eso**. La lista de modificadores disponibles (`withAndroidManifest`, `withInfoPlist`, `withEntitlementsPlist`, `withGradleProperties`, `withAppBuildGradle`, entre otros) está en https://docs.expo.dev/config-plugins/plugins/.

### Módulos nativos locales

Cuando lo que necesitas es **código** nativo (una función en Kotlin o Swift), tampoco hace falta salir de managed. La **Expo Modules API** permite crear un módulo local dentro del repositorio:

```sh
npx create-expo-module@latest --local notes-haptics
```

Genera `modules/notes-haptics/` con un archivo Swift, uno Kotlin y su definición en TypeScript, más un config plugin propio si lo necesita. Prebuild lo enlaza automáticamente y EAS Build lo compila como cualquier otra dependencia. En la etapa de nativo viste el patrón desde el lado de JavaScript; aquí la novedad es que sigue funcionando con CNG.

### Cuándo sí y cuándo no

| Necesidad                                                     | Solución                                    |
| ------------------------------------------------------------- | ------------------------------------------- |
| Un campo de `Info.plist` o `AndroidManifest.xml`              | Campo de `app.config.ts` si existe; si no, config plugin local |
| Cambiar Gradle, Podfile o entitlements                        | Config plugin local                         |
| Una librería con código nativo                                | `npx expo install`; trae su propio plugin   |
| Código nativo propio (Kotlin/Swift)                           | Módulo local con Expo Modules API           |
| Un SDK de terceros que exige editar archivos nativos a mano   | Primero intenta un config plugin; muchos "requisitos manuales" son cambios de manifest o plist |
| Un proyecto heredado con `ios/` y `android/` muy personalizados | Mantener las carpetas en el repositorio (workflow bare), sabiendo que pierdes CNG |

La última fila es la única en la que "salir de managed" tiene sentido. Incluso entonces, el resto del tooling (EAS Build, Submit, Update, Expo Router) sigue funcionando: solo dejas de regenerar los proyectos nativos. La CLI de React Native sin Expo existe, pero no es el siguiente paso natural de un proyecto Expo: implica renunciar a prebuild, a los plugins y a la gestión de credenciales que llevas toda la etapa usando.

## Errores comunes

**Editar `AndroidManifest.xml` a mano tras un prebuild.** Funciona en local y desaparece en el siguiente build de EAS. Ocurre porque las carpetas nativas son generadas y EAS las regenera desde cero. Se detecta porque el build en la nube no tiene tu cambio. Solución: mueve el cambio a un config plugin o a un campo de `app.config.ts`.

**Plugin que duplica entradas en cada prebuild.** El manifest acaba con tres permisos iguales o el plist con claves repetidas y el build falla o Google Play advierte. Ocurre porque el plugin agrega sin comprobar. Se detecta ejecutando `prebuild --clean` dos veces y comparando. Haz cada modificación idempotente.

**Hacer commit de `ios/` y `android/` "por si acaso".** El repositorio pesa más, los conflictos de merge en archivos generados se multiplican y `prebuild` deja de aplicarse en EAS. Ocurre por copiar hábitos de proyectos sin Expo. Se detecta porque cambios en `app.config.ts` (icono, permisos) dejan de reflejarse en los builds. Mantén las carpetas en `.gitignore` salvo que hayas decidido conscientemente pasar al workflow bare.
