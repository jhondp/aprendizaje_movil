## Objetivo

Al terminar esta lección podrás crear variables de entorno en EAS para `development`, `preview` y `production` con la visibilidad correcta, y explicar cuáles llegan al bundle de la app y cuáles solo existen en el servidor de build.

**Prerrequisitos:** `10-build-release-operaciones/00-app-config-y-entornos`

## Concepto

En la etapa de seguridad aprendiste que un secreto no debe vivir en el repositorio. Ahora que los builds se hacen en un servidor que no es tu máquina, aparece la pregunta práctica: si el archivo `.env` no se sube a Git, ¿de dónde saca EAS los valores cuando construye la app?

Piensa en una caja fuerte de hotel. Tú dejas allí lo valioso y el hotel se ocupa de que solo tu habitación acceda a esa caja. No llevas el pasaporte en el bolsillo a la piscina (el repositorio), pero tampoco lo tiras: lo guardas en un lugar que sabe quién eres. Las **variables de entorno de EAS** son esa caja fuerte: viven en los servidores de Expo, asociadas a tu proyecto y a un entorno, y se inyectan en el build cuando hace falta.

### Tres entornos, tres conjuntos de valores

EAS define tres entornos con nombre fijo: `development`, `preview` y `production`. Cada variable pertenece a uno o varios de ellos. Coinciden con las variantes de la lección anterior, y no es casualidad: en la próxima lección cada perfil de `eas.json` se conecta con uno de estos entornos. La referencia completa está en https://docs.expo.dev/eas/environment-variables/.

Una variable típica:

| Nombre                 | development                  | preview                          | production                   |
| ---------------------- | ---------------------------- | -------------------------------- | ---------------------------- |
| `APP_VARIANT`          | `development`                | `preview`                        | `production`                 |
| `EXPO_PUBLIC_API_URL`  | `http://localhost:3000`      | `https://staging.example.com`    | `https://api.example.com`    |
| `SENTRY_AUTH_TOKEN`    | (no definida)                | `sntrys_...`                     | `sntrys_...`                 |

### Público o secreto: el prefijo decide

Aquí está la regla más importante de la lección. Expo solo incluye en el bundle de JavaScript las variables cuyo nombre empieza por `EXPO_PUBLIC_`. Cualquier otra variable existe únicamente donde se ejecuta el build o donde se evalúa `app.config.ts`; la app instalada nunca la ve.

```ts
// Available inside the app: it is inlined into the JS bundle at build time.
const apiUrl = process.env.EXPO_PUBLIC_API_URL;

// undefined inside the app: no EXPO_PUBLIC_ prefix, so it never leaves the build server.
const token = process.env.SENTRY_AUTH_TOKEN;
```

La consecuencia es directa: **todo lo que lleve `EXPO_PUBLIC_` es público**. Cualquier persona con el archivo `.apk` o `.ipa` puede leerlo. Sirve para URLs, identificadores de proyecto o claves que el proveedor diseñó para ser públicas (como la clave publicable de un servicio de pagos). No sirve para tokens de servidor, claves privadas ni contraseñas. Si un valor tiene que ser secreto, no lleva el prefijo y, por tanto, solo puede usarlo `app.config.ts` o un paso del build.

<Callout kind="danger">
  Todo lo que `app.config.ts` devuelve, `extra` incluido, viaja dentro de la app y se ve con `npx expo config --type public`. Nunca copies una variable sin prefijo a `extra` ni a ningún otro campo de configuración (por ejemplo, `extra: { sentryToken: process.env.SENTRY_AUTH_TOKEN }` publica el token). Usa los secretos solo en pasos del build, como la subida de source maps. Además, las variables con visibilidad `secret` no están disponibles cuando EAS CLI resuelve la configuración en tu máquina, así que tampoco sirven para decidir valores de `app.config.ts`.
</Callout>

### Visibilidad en EAS

Al crear una variable eliges una **visibilidad** que controla quién puede volver a leer su valor:

- `plaintext`: se ve en el panel web y en la terminal. Para valores que de todos modos son públicos.
- `sensitive`: se ve en el panel si lo pides expresamente y se oculta en los logs de build. Para valores que no son secretos pero tampoco quieres exponer por descuido.
- `secret`: nunca se vuelve a mostrar, ni en el panel ni con `eas env:list`. Solo el servidor de build lo lee. Para tokens y claves privadas.

Visibilidad y prefijo son independientes: una variable `EXPO_PUBLIC_` con visibilidad `secret` sigue acabando dentro del bundle. La visibilidad protege el panel; el prefijo protege la app.

### Los comandos

La familia de comandos es `eas env:*` y reemplaza a los antiguos `eas secret:*`, que todavía aparecen en tutoriales viejos. Los que vas a usar:

```sh
# Create a variable in one environment
eas env:create --environment production --name EXPO_PUBLIC_API_URL --value https://api.example.com --visibility plaintext

# Create a secret that the build server can read but nobody can print again
eas env:create --environment production --name SENTRY_AUTH_TOKEN --value sntrys_xxx --visibility secret

# See what exists in an environment
eas env:list --environment production

# Download the development variables into a local .env.local for npx expo start
eas env:pull --environment development
```

`eas env:pull` escribe `.env.local`, que debe estar en `.gitignore`. Los valores con visibilidad `secret` no se descargan: en el archivo aparecen con un comentario que indica que el valor se omitió. Es la conducta esperada, no un error. La guía detallada está en https://docs.expo.dev/eas/environment-variables/manage/.

<Callout kind="danger">
  Si alguna vez subiste un secreto al repositorio, cambiarlo por una variable de EAS no basta: el valor sigue en el historial de Git. Revoca el secreto en el proveedor y genera uno nuevo antes de guardarlo en EAS.
</Callout>

### Cómo llegan las variables al build

Cuando EAS construye con un perfil enlazado al entorno `production`, carga todas las variables de ese entorno antes de evaluar `app.config.ts` y de empaquetar el JavaScript. Así `APP_VARIANT` decide el identificador (como viste en la lección anterior) sin que la escribas a mano, y `EXPO_PUBLIC_API_URL` queda incrustada en el bundle con el valor de producción. La conexión perfil-entorno la verás en detalle en la próxima lección; por ahora basta con saber que existe.

## Errores comunes

**Guardar un token de servidor como `EXPO_PUBLIC_`.** Se ve como una app que "funciona" porque el token está disponible en el código. Ocurre porque el prefijo es la única forma de leer la variable desde un componente, y es tentador usarlo para todo. Se detecta descomprimiendo el `.apk` y buscando el valor en el bundle: aparece en texto plano. Solución: mover la operación que necesita el token a un backend y dejar en la app solo valores públicos.

**Crear la variable en un solo entorno.** El build de producción falla o usa `undefined` porque la variable solo existe en `development`. Se detecta con `eas env:list --environment production`: la variable no está. Crea cada variable en todos los entornos donde el código la lee, aunque el valor sea el mismo.

**Esperar que `eas env:pull` traiga los secretos.** El archivo `.env.local` aparece sin el valor y crees que el comando falló. Ocurre porque los valores `secret` nunca se descargan por diseño. Si necesitas ese valor en tu máquina, no era un secreto de build: cámbialo a `sensitive` o define un valor de desarrollo distinto.
