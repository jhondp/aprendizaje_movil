## Objetivo

Al terminar esta lección podrás instalar Sentry en la app con el wizard y el config plugin de Expo, subir source maps desde EAS Build, capturar un error manejado con contexto útil y definir un objetivo de crash-free rate para producción.

**Prerrequisitos:** `10-build-release-operaciones/08-versionado-y-changelog`

## Concepto

Una vez publicada, la app corre en miles de teléfonos que no puedes ver. Cuando algo falla, el usuario no abre un issue: cierra la app. Sin monitoreo, te enteras por una reseña de una estrella semanas después. **Sentry** es el servicio de monitoreo de errores más usado con React Native: recibe cada excepción con su stack trace, el dispositivo, la versión y el contexto que tú agregues.

Piensa en la caja negra de un avión. No evita el fallo, pero registra todo lo que pasó antes para que se pueda entender y corregir. Sentry es la caja negra de la app, con una diferencia: te avisa mientras el avión sigue volando, para que publiques un rollback antes de que afecte a más gente.

### Instalar con el wizard

Sentry mantiene un asistente que hace la configuración completa (https://docs.expo.dev/guides/using-sentry/):

```sh
npx @sentry/wizard@latest -i reactNative
```

El wizard pide iniciar sesión en Sentry, elige o crea el proyecto y hace tres cosas en tu repositorio:

1. Instala `@sentry/react-native` con la versión compatible con tu SDK.
2. Agrega el **config plugin** `@sentry/react-native/expo` a la configuración. Con `app.config.ts` te mostrará el bloque para que lo agregues a mano:

```ts
plugins: [
  [
    "@sentry/react-native/expo",
    {
      organization: "<sentry-org-slug>",
      project: "<sentry-project-slug>",
      url: "https://sentry.io/",
    },
  ],
],
```

3. Añade `Sentry.init` y envuelve el componente raíz. Con Expo Router, el lugar es `app/_layout.tsx`:

```tsx
import * as Sentry from "@sentry/react-native";
import { Stack } from "expo-router";

Sentry.init({
  dsn: "https://<public-key>@o<org-id>.ingest.sentry.io/<project-id>",
  sendDefaultPii: false,
  tracesSampleRate: 0.2,
});

function RootLayout() {
  return <Stack />;
}

export default Sentry.wrap(RootLayout);
```

El **DSN** es la dirección a la que la app envía eventos. Es pública por diseño (va dentro del bundle), así que puede ir en `EXPO_PUBLIC_SENTRY_DSN` sin problema. `sendDefaultPii: false` evita enviar datos personales por defecto; `tracesSampleRate` controla qué fracción de sesiones envía datos de rendimiento (0.2 es un 20 %; en producción, empieza bajo).

Como el plugin agrega código nativo, necesitas un build nuevo: es un cambio de los que no viajan por OTA.

### Source maps: leer el stack trace

Un stack trace de producción sin source maps apunta a `index.android.bundle:1:48213`, inútil. El config plugin sube los source maps a Sentry durante `eas build`, pero necesita autenticarse: un token de Sentry con permiso para subir. Ese token es un secreto de build, exactamente el caso de la lección de variables:

```sh
eas env:create --environment production --name SENTRY_AUTH_TOKEN --value sntrys_xxx --visibility secret
```

Repítelo para `preview`. Con eso, cada error en Sentry muestra el archivo `.tsx` y la línea real. Para actualizaciones OTA, el plugin también sube los source maps al ejecutar `eas update`, siempre que el token esté en el entorno donde corre el comando.

### Capturar errores manejados

Sentry captura por sí solo los errores no manejados que cierran la app. Pero muchos fallos importantes son **manejados**: un `try/catch` que muestra "no se pudo guardar" y sigue. Esos no llegan a Sentry a menos que los envíes:

```ts
import * as Sentry from "@sentry/react-native";

export async function saveNote(note: Note): Promise<boolean> {
  try {
    await repository.save(note);
    return true;
  } catch (error) {
    Sentry.captureException(error, {
      tags: { feature: "notes", action: "save" },
      extra: { noteId: note.id, titleLength: note.title.length },
    });
    return false;
  }
}
```

Las **tags** son etiquetas por las que puedes filtrar y agrupar; `extra` es contexto libre. No pongas contenido del usuario (el texto de la nota) en `extra`: es dato personal y termina en un servicio de terceros que declaraste en la política de privacidad. Envía identificadores y medidas, no contenido.

También ayudan las **breadcrumbs**, migas que registran qué hizo el usuario antes del error (`Sentry.addBreadcrumb({ category: "navigation", message: "opened note detail" })`). Sentry agrega varias automáticamente (navegación, peticiones de red, toques).

### La métrica que importa: crash-free rate

Sentry muestra dos porcentajes por versión: **crash-free sessions** (sesiones que terminaron sin crash) y **crash-free users** (usuarios que no sufrieron ningún crash en el periodo). Son la forma más honesta de responder "¿está bien la versión que acabo de publicar?". Define un objetivo antes de lanzar y una acción si no se cumple. Un punto de partida habitual:

- Objetivo: crash-free sessions por encima del 99,5 % en las primeras 24 horas de cada release.
- Acción si cae por debajo: rollback OTA si el cambio fue JS; si fue nativo, congelar el despliegue en la tienda (Google Play permite lanzamientos graduales por porcentaje de usuarios) y preparar un build de corrección.
- Alerta: configura en Sentry una alerta por correo o chat cuando un nuevo tipo de error supere un umbral de usuarios afectados.

<Callout kind="tip">
  Envía un error de prueba desde el build de preview antes del primer release (un botón oculto que ejecute `Sentry.captureException(new Error("Sentry smoke test"))`). Si no aparece en el panel en un minuto, el DSN, el entorno o el build están mal, y es mejor descubrirlo ahora que después de una reseña.
</Callout>

Este Snack reproduce la parte de la lógica que sí puedes ejecutar aquí: un `try/catch` que captura un error manejado con tags y contexto. En lugar de `@sentry/react-native` (que necesita un build nativo), usa una función `captureException` de la misma forma que guarda los eventos en una lista visible. En tu app real, sustituye esa función por `Sentry.captureException`.

<Snack

import { Button, FlatList, StyleSheet, Text, View } from "react-native";

type Event = { message: string; tags: Record<string, string>; extra: Record<string, number> };

export default function App() {
  const [events, setEvents] = useState<Event[]>([]);

  // Stand-in for Sentry.captureException: same shape, local inbox instead of the network.
  function captureException(error: unknown, context: { tags: Record<string, string>; extra: Record<string, number> }) {
    const message = error instanceof Error ? error.message : String(error);
    setEvents((prev) => [{ message, ...context }, ...prev]);
  }

  async function saveNote(title: string): Promise<boolean> {
    try {
      if (title.length > 20) throw new Error("Title too long for storage");
      return true;
    } catch (error) {
      captureException(error, { tags: { feature: "notes", action: "save" }, extra: { titleLength: title.length } });
      return false;
    }
  }

  return (
    <View style={styles.container}>
      <Button title="Save short note" onPress={() => saveNote("Groceries")} />
      <Button title="Save very long note" onPress={() => saveNote("A title that is definitely too long")} />
      <Text style={styles.heading}>Captured events: {events.length}</Text>
      <FlatList
        data={events}
        keyExtractor={(_, i) => String(i)}
        renderItem={({ item }) => (
          <Text style={styles.event}>{item.message} · {item.tags.feature}/{item.tags.action} · titleLength={item.extra.titleLength}</Text>
        )}
      />
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, paddingTop: 80, paddingHorizontal: 16, gap: 12 },
  heading: { fontSize: 18, fontWeight: "600" },
  event: { paddingVertical: 6 },
});`}

## Errores comunes

**Stack traces sin archivo ni línea.** Los errores llegan pero apuntan a `index.android.bundle`. Ocurre porque faltó `SENTRY_AUTH_TOKEN` en el entorno del build y los source maps no se subieron. Se detecta en el log de `eas build`: no aparece la línea de "Uploading source maps". Crea el token como secret en cada entorno y reconstruye.

**Enviar contenido del usuario en `extra`.** El texto de las notas queda almacenado en Sentry. Ocurre por comodidad al depurar. Se detecta revisando cualquier evento en el panel: si puedes leer datos de un usuario, hay un problema de privacidad y una declaración de datos falsa en la tienda. Envía longitudes, identificadores y estados, nunca contenido.

**Instalar Sentry y publicarlo por OTA.** La actualización llega, `Sentry.init` intenta acceder al módulo nativo que no existe en el build instalado y la app se cierra al arrancar. Ocurre porque el SDK tiene código nativo. Se detecta porque el crash aparece solo tras la actualización. Rollback inmediato y build nuevo con el plugin.
