## Objetivo

Al terminar esta lección podrás explicar la diferencia entre Expo Go y un development build, y crear un development build local con `expo-dev-client`.

**Prerrequisitos:** `04-react-native-expo/01-crear-proyecto-con-expo`

## Concepto

Una app de React Native tiene dos capas. La capa **nativa** es el binario que se instala en el teléfono: código Swift, Kotlin y C++ compilado, con todas las librerías nativas que usa tu app. La capa **JavaScript** es tu bundle: componentes, pantallas y lógica. Metro sirve la capa JavaScript; la capa nativa hay que compilarla.

Documentación oficial: https://docs.expo.dev/develop/development-builds/introduction/

### Una analogía: la consola de videojuegos

Expo Go es como una consola de videojuegos que ya compraste: trae un hardware fijo y puedes insertar cualquier juego (tu bundle de JavaScript) siempre que ese juego no pida un accesorio que la consola no tiene. Un development build es fabricar tu propia consola: tarda más, pero puedes conectarle cualquier accesorio que necesites.

### Expo Go

Expo Go es una app que Expo publica con una capa nativa ya compilada. Incluye los módulos del SDK de Expo (cámara, ubicación, notificaciones básicas, sensores, entre otros) y el cliente para conectarse a Metro. Por eso puedes crear un proyecto y verlo en tu teléfono en un minuto, sin instalar Xcode ni Android Studio.

Sus límites son los de la consola fija:

- Solo puedes usar las librerías nativas que ya vienen dentro de Expo Go. Si instalas una librería con código nativo propio que no está incluida, la app falla al importarla.
- No puedes cambiar la configuración nativa: el nombre del paquete, los permisos, el ícono o los plugins de configuración no se aplican.
- Soporta un solo SDK de Expo por versión.

Expo describe a Expo Go como un entorno para aprender y prototipar, no para construir apps de producción.

### Development build

Un development build es **tu propia versión de Expo Go**: un binario compilado con exactamente las librerías nativas y la configuración de tu proyecto, más la librería `expo-dev-client`, que agrega un menú de desarrollo, un selector de servidores y mejores herramientas de depuración.

Para crear uno local:

```bash
npx expo install expo-dev-client
npx expo run:ios      # macOS with Xcode
npx expo run:android  # Android Studio and an emulator or a device
```

`npx expo install` es distinto de `npm install`: consulta qué versión de cada paquete es compatible con el SDK de tu proyecto e instala esa. Úsalo siempre para paquetes de Expo y de React Native.

`npx expo run:ios` hace tres cosas: genera las carpetas nativas `ios/` y `android/` a partir de `app.json` y de tus dependencias (este paso se llama **prebuild**), compila el binario e instala la app en el simulador o dispositivo. La primera vez tarda varios minutos. Después, mientras solo cambies JavaScript, basta con `npx expo start`: el development build se conecta a Metro igual que Expo Go.

Las carpetas `ios/` y `android/` son generadas. Expo recomienda no editarlas a mano y regenerarlas cuando cambias la configuración nativa; esta idea se llama Continuous Native Generation.

Si no tienes macOS o no quieres instalar Android Studio, también puedes compilar el development build en la nube con EAS Build. Lo verás en detalle en la etapa dedicada a builds y publicación.

### Cuándo reconstruir

Necesitas compilar de nuevo el development build solo cuando cambia la capa nativa:

- instalas o actualizas una librería con código nativo,
- cambias `app.json` en algo que afecta al binario (permisos, ícono, plugins),
- actualizas el SDK de Expo.

Si solo cambias componentes, estilos o lógica, Fast Refresh se encarga y no hace falta compilar.

### Cuál elegir

Para esta etapa, Expo Go o Snack alcanzan: todo lo que usarás viene incluido en el SDK. En cuanto tu proyecto necesite una librería nativa externa o una configuración propia, pasa a un development build. En un proyecto profesional, lo habitual es trabajar con development builds desde el principio, porque es el mismo binario que después se publica.

## Errores comunes

**Instalar una librería nativa y seguir usando Expo Go.** La app muestra un error como "Cannot find native module" o "TurboModuleRegistry.getEnforcing(...) could not be found". Ocurre porque Expo Go no incluye esa librería y no se puede agregar. Se detecta porque el error aparece justo al importar la librería. Solución: crear un development build.

**Usar npm install para paquetes de Expo.** La app compila pero falla al arrancar, o aparecen advertencias de versiones incompatibles. Ocurre porque npm instala la última versión publicada, que puede pertenecer a otro SDK. Se detecta con `npx expo install --check`, que lista los paquetes con versión incorrecta.

**Editar a mano las carpetas ios/ y android/.** Los cambios desaparecen la próxima vez que se ejecuta prebuild. Ocurre porque esas carpetas se generan desde `app.json` y las dependencias. Se detecta porque `git diff` muestra que tus cambios se perdieron tras reconstruir. Solución: usar la configuración de `app.json` o un config plugin.
