## Objetivo

Al terminar esta lección podrás verificar que toda la comunicación de tu app va por HTTPS sin excepciones, extraer el hash de clave pública de tu API con `openssl`, y documentar una decisión razonada sobre certificate pinning para tu proyecto.

**Prerrequisitos:** `09-seguridad-movil/03-almacenamiento-seguro`

## Concepto

Esta lección cubre **MASVS-NETWORK-1** (todo el tráfico de red protegido según las prácticas actuales) y **MASVS-NETWORK-2** (pinning de identidad para los endpoints bajo control del desarrollador).

### El sobre cerrado y la firma del cartero

Enviar datos por HTTP es mandar una postal: cualquiera que la toque en el camino la lee y puede reescribirla. HTTPS, es decir HTTP sobre TLS, mete la postal en un sobre cerrado (cifrado) y además comprueba que el cartero es quien dice ser (autenticación del servidor mediante su certificado). El sistema operativo trae una lista de autoridades certificadoras (CA) en las que confía; si el certificado de tu API está firmado por una de ellas, la conexión se acepta.

El pinning va un paso más: además de exigir un sobre cerrado, tu app solo acepta al cartero cuya firma concreta guardaste de antemano. Si alguien logra instalar una CA falsa en el dispositivo (una red corporativa, un proxy de inspección, malware), el sobre seguiría pareciendo válido para el sistema, pero no para tu app.

### MASVS-NETWORK-1: HTTPS siempre, sin puertas traseras

Las plataformas ya bloquean el tráfico en claro por defecto: Android desde la versión 9 y iOS mediante App Transport Security (ATS). El riesgo no es olvidar activar HTTPS, sino **desactivar** esas protecciones para salir de un apuro en desarrollo y dejarlo así:

- En iOS, `NSAllowsArbitraryLoads: true` dentro de `NSAppTransportSecurity` apaga ATS para toda la app.
- En Android, `android:usesCleartextTraffic="true"` permite HTTP a cualquier dominio.

Con Expo, esas claves se configuran desde `app.json` (`ios.infoPlist`) o mediante config plugins. Búscalas en tu proyecto: si aparecen, son un hallazgo. Para desarrollo local con Metro no las necesitas; Expo configura excepciones acotadas al servidor de desarrollo.

Además de no romper los valores por defecto, la app debe cumplir dos cosas: que **todas** las URLs sean `https://` (revisa constantes, `.env`, deep links y URLs construidas dinámicamente) y que el servidor tenga TLS bien configurado (certificado vigente, versiones modernas del protocolo, HSTS). La guía oficial de React Native resume el punto de partida: [https://reactnative.dev/docs/security#networking](https://reactnative.dev/docs/security#networking).

### Leer el certificado de tu API

Antes de hablar de pinning necesitas ver con qué estás tratando. `openssl s_client` abre una conexión TLS y muestra el certificado; encadenado con `openssl x509` extraes los campos. El **hash SPKI** (SHA-256 de la clave pública, en base64) es el valor que se fija en un pin, porque sobrevive a renovaciones del certificado mientras la clave no cambie. Lo harás en la práctica.

### MASVS-NETWORK-2: pinning, con su factura

El pinning protege contra un atacante que controla las CA del dispositivo. Su costo es operativo, y es alto:

- **Rotación.** Cuando renueves el certificado con una clave nueva, o cambies de proveedor, la app con pins antiguos deja de conectar. Los usuarios que no actualicen quedan bloqueados. Por eso todo pin set lleva al menos un **pin de respaldo** para una clave que aún no está en producción, y a veces una **fecha de expiración** tras la cual el pinning se desactiva.
- **Terceros.** Solo se hace pinning de endpoints que controlas. Fijar la clave de una API ajena es apostar a que ese proveedor nunca rote.
- **Depuración.** Las herramientas de inspección de tráfico dejan de funcionar; conviene desactivar el pinning en builds de desarrollo.

En Expo, el pinning necesita código nativo, así que **no funciona en Expo Go ni existe una solución en JavaScript puro**: hace falta un development build (o un build de producción) y una de estas rutas:

**Ruta 1: configuración de plataforma.** En iOS, ATS admite pins declarativos en `Info.plist` (iOS 14 o superior). Desde `app.json`:

```json
{
  "expo": {
    "ios": {
      "infoPlist": {
        "NSAppTransportSecurity": {
          "NSPinnedDomains": {
            "api.notes.example.com": {
              "NSIncludesSubdomains": false,
              "NSPinnedLeafIdentities": [
                { "SPKI-SHA256-BASE64": "PRIMARY_PIN_BASE64_HERE" },
                { "SPKI-SHA256-BASE64": "BACKUP_PIN_BASE64_HERE" }
              ]
            }
          }
        }
      }
    }
  }
}
```

En Android, el equivalente es un archivo `res/xml/network_security_config.xml` referenciado desde el manifiesto ([https://developer.android.com/privacy-and-security/security-config](https://developer.android.com/privacy-and-security/security-config)). Expo no lo genera por ti: hace falta un config plugin que escriba el archivo y modifique el manifiesto en `prebuild`.

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
  <domain-config>
    <domain includeSubdomains="false">api.notes.example.com</domain>
    <pin-set expiration="2027-06-30">
      <pin digest="SHA-256">PRIMARY_PIN_BASE64_HERE</pin>
      <pin digest="SHA-256">BACKUP_PIN_BASE64_HERE</pin>
    </pin-set>
  </domain-config>
</network-security-config>
```

**Ruta 2: una biblioteca con módulo nativo.** `react-native-ssl-public-key-pinning` usa OkHttp en Android y TrustKit en iOS, se instala con `npx expo install` y se configura desde JavaScript al arrancar. Sigue necesitando un development build, pero evita escribir el plugin a mano:

```ts
import { initializeSslPinning } from "react-native-ssl-public-key-pinning";

export async function setupPinning() {
  if (__DEV__) return; // keep traffic inspectable during development
  await initializeSslPinning({
    "api.notes.example.com": {
      includeSubdomains: false,
      publicKeyHashes: ["PRIMARY_PIN_BASE64_HERE", "BACKUP_PIN_BASE64_HERE"],
    },
  });
}
```

Que los pins vivan en JavaScript tiene una consecuencia útil: puedes rotarlos con una actualización OTA sin pasar por las tiendas.

### ¿Vale la pena para tu app?

MASVS sitúa el pinning en el perfil **MAS-L2**. Para la app de notas, que apunta a MAS-L1, la decisión razonable es documentar que **no** haces pinning, que dependes de TLS con configuración moderna y HSTS en el servidor, y qué condición haría cambiar la decisión (por ejemplo, empezar a manejar datos de salud o pagos). Una decisión escrita y justificada cumple la auditoría mejor que un pinning mal operado que bloquea a tus usuarios en la próxima renovación.

<Callout kind="warning">
  Un pinning sin pin de respaldo es una bomba de tiempo: en la siguiente rotación de clave la app deja de funcionar para todo el que no actualice. Si decides hacer pinning, el pin de respaldo y el calendario de rotación forman parte del control, no son opcionales.
</Callout>

## Errores comunes

**Apagar ATS o permitir cleartext "solo para probar".** El flag se agrega para conectar con un servidor de pruebas sin certificado y nadie lo quita. Ocurre porque el efecto es invisible en la app. Se detecta buscando `NSAllowsArbitraryLoads` y `usesCleartextTraffic` en `app.json` y en config plugins.

**Fijar el hash del certificado en lugar del de la clave pública.** El pin deja de coincidir en la siguiente renovación automática (Let's Encrypt renueva cada 90 días) aunque la clave sea la misma. Ocurre por copiar el `fingerprint` del certificado en vez del hash SPKI. Se detecta porque el pinning falla justo después de una renovación sin cambio de clave.

**Hacer pinning sin pin de respaldo ni plan de rotación.** Todo funciona hasta que cambia la clave del servidor, y entonces la app queda inutilizable para quien no actualice. Se detecta revisando la configuración: un solo pin es un hallazgo en sí mismo.

**Esperar que el pinning funcione en Expo Go.** La configuración se agrega y "no hace nada". Ocurre porque el pinning necesita código nativo y Expo Go no puede incluir el tuyo. Se detecta probando con un proxy de inspección en un development build: si el tráfico se ve, el pinning no está activo.
