## Objetivo

Al terminar esta lección podrás extraer las cadenas de texto de tu propio bundle, decidir qué valores pueden viajar como `EXPO_PUBLIC_` y cuáles deben quedarse en el servidor, y dejar `.env` fuera del repositorio.

**Prerrequisitos:** `09-seguridad-movil/01-owasp-mobile-top-10-y-masvs`

## Concepto

Esta lección cubre **MASVS-STORAGE-2** (evitar la fuga de datos sensibles) y **MASVS-CODE** en su vertiente de configuración segura; también roza **MASVS-CRYPTO-2**, porque una clave de API dentro del bundle es una clave mal gestionada.

### El bundle es un folleto, no una caja fuerte

Cuando publicas tu app, el JavaScript que escribiste se compila en un bundle y viaja dentro del archivo `.apk`, `.aab` o `.ipa`. Cualquier persona que instale la app tiene ese archivo. Es un folleto que repartes en la calle: puedes imprimirlo con letra pequeña, pero no puedes evitar que alguien lo lea con lupa. Todo lo que está en el bundle es público. No importa si la variable se llama `SECRET_KEY`, si está codificada en base64 o si la ofuscas: sigue estando en el folleto.

Por eso la regla es corta: **un secreto es algo que, si se filtra, alguien puede actuar en tu nombre**. Una clave privada de pagos, una clave de servicio de Firebase, la contraseña de una base de datos, un token de una API de terceros que cobra por uso. Nada de eso puede estar en el bundle.

### Qué hace Expo con `EXPO_PUBLIC_`

Expo CLI lee los archivos `.env` de tu proyecto y, cuando compila, **reemplaza** cada referencia `process.env.EXPO_PUBLIC_NOMBRE` por su valor literal. La documentación lo dice sin rodeos: "Do not store sensitive info, such as private keys, in `EXPO_PUBLIC_` variables. These variables will be visible in plain-text in your compiled application" (<https://docs.expo.dev/guides/environment-variables/>).

```ts
// .env
// EXPO_PUBLIC_API_URL=https://api.notes.example.com

// src/config.ts
export const API_URL = process.env.EXPO_PUBLIC_API_URL;
// After bundling this line becomes, literally:
// export const API_URL = "https://api.notes.example.com";
```

El prefijo es una advertencia, no una protección. Las variables sin prefijo no se inyectan en el bundle, pero tampoco existen en el dispositivo: solo están disponibles en tu máquina o en el servidor de build (por ejemplo, en `app.config.ts`). Dos detalles prácticos: solo se reemplaza la forma `process.env.EXPO_PUBLIC_X` con notación de punto (`process.env["EXPO_PUBLIC_X"]` no se inyecta), y el código dentro de `node_modules` no se toca.

Entonces, ¿para qué sirve `EXPO_PUBLIC_`? Para **configuración**: la URL de la API, el identificador público de un proyecto de analítica, una feature flag, el nombre del entorno. Datos que cambian entre staging y producción y que no dan poder a quien los lea.

### Configuración o secreto: la pregunta que decide

Antes de escribir una variable pregúntate: si publico este valor en la descripción de la app en la tienda, ¿qué puede hacer un desconocido con él?

- URL de la API: nada que no pueda hacer ya con la app instalada. **Configuración.**
- Clave "publishable" de un proveedor de pagos: está diseñada para ser pública; el proveedor limita lo que permite. **Configuración**, aunque revisa las restricciones en su consola.
- Clave de servidor de un proveedor de pagos, correo o notificaciones: cobrar, enviar correos en tu nombre. **Secreto.**
- Clave de una API de mapas restringida por bundle id: la restricción la aplica el proveedor, no tu app. **Configuración**, con la restricción activada.

### Dónde viven los secretos: en el servidor

Si la app no puede tener el secreto, el trabajo que lo necesita lo hace tu backend. El patrón se llama a veces **BFF** (backend for frontend) o capa de orquestación: la app llama a tu API con la sesión del usuario, y tu API usa el secreto para hablar con el tercero.

```ts
// app: no key here, only the user's session
export async function requestUploadUrl(noteId: string, session: string) {
  const res = await fetch(`${API_URL}/notes/${noteId}/upload-url`, {
    method: "POST",
    headers: { Authorization: `Bearer ${session}` },
  });
  return (await res.json()) as { url: string };
}
```

```ts
// server (for example a route in your Node backend from stage 8)
// STORAGE_SECRET lives only in the server's environment
app.post("/notes/:id/upload-url", requireSession, async (req, res) => {
  const url = await storage.signUploadUrl(req.params.id, process.env.STORAGE_SECRET!);
  res.json({ url });
});
```

Ventaja adicional: si el secreto se filtra en el servidor, lo rotas ahí sin publicar una versión nueva de la app.

### Y los secretos de build

EAS Build permite definir variables de entorno con visibilidad `secret` que solo existen durante la compilación (por ejemplo, credenciales para subir source maps). Son secretos del proceso de build, no de la app: si los expones vía `EXPO_PUBLIC_` acaban igualmente en el bundle. Úsalos para el build, nunca como atajo para "esconder" una clave en la app.

### Tres comprobaciones que puedes hacer hoy

1. **Mira dentro del bundle.** Exporta la app y busca los valores que sospechas. Lo harás en la práctica.
2. **Saca `.env` del repositorio.** `.env*` en `.gitignore` y `git rm --cached .env` si ya lo habías subido. Un secreto que estuvo en un commit debe considerarse filtrado y rotarse, aunque borres el archivo después.
3. **Busca secretos en el historial.** `git log -p -S "<fragmento>"` muestra si un valor apareció alguna vez.

<Callout kind="danger">
  Un secreto que llegó al bundle o a un commit ya no es secreto. Borrarlo del código no lo recupera: hay que rotarlo (generar uno nuevo e invalidar el anterior) en el servicio que lo emitió.
</Callout>

## Errores comunes

**Creer que codificar es cifrar.** La clave se guarda en base64 o se parte en dos cadenas concatenadas "para que no se vea". Ocurre por confundir ofuscar con proteger: el código que la reconstruye está en el mismo bundle. Se detecta ejecutando el bundle exportado en Node y llamando a la función que devuelve la clave, o con `grep` del prefijo conocido del proveedor.

**Confiar en `.gitignore` como única defensa.** El archivo `.env` se agregó a `.gitignore` después de haberlo subido, y sigue en el historial. Ocurre porque `.gitignore` solo evita añadir archivos nuevos, no borra los ya rastreados. Se detecta con `git log --all -- .env`; si hay resultados, rota los secretos.

**Leer la variable con corchetes o desestructuración.** `const { EXPO_PUBLIC_API_URL } = process.env` funciona en desarrollo web y devuelve `undefined` en la app. Ocurre porque Expo solo inyecta la forma `process.env.EXPO_PUBLIC_X` con notación de punto. Se detecta porque las peticiones van a `undefined/notes`.
