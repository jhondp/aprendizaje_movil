## Objetivo

Al terminar esta lección podrás identificar las fronteras de confianza de tu app, validar lo que cruza cada una con un esquema zod y garantizar que ninguna consulta SQL se construye concatenando texto del usuario.

**Prerrequisitos:** `09-seguridad-movil/04-https-y-certificate-pinning`

## Concepto

Esta lección cubre **MASVS-CODE-4**: la app valida y sanea toda entrada no confiable. Toca también **MASVS-PLATFORM-1**, porque los deep links son una de esas entradas.

### El control de acceso del edificio

En un edificio de oficinas nadie llega a su escritorio sin pasar por recepción: se comprueba quién eres y a dónde vas, y solo entonces se abre el torno. Dentro, ya no te vuelven a pedir identificación en cada puerta. Una app funciona igual: define **fronteras de confianza** y valida todo lo que las cruza, para que el código interior pueda trabajar con datos que ya sabe correctos. Si la recepción falla, el resto del edificio queda expuesto.

### Dónde están las fronteras

Toda entrada que no generó tu propio código es no confiable, aunque venga de una fuente que parece amiga:

- **Formularios**: el usuario puede escribir cualquier cosa, incluidos textos enormes o caracteres que tu base de datos interpreta.
- **Deep links y parámetros de ruta**: cualquier app o página web puede abrir `notes://note/abc` con el valor que quiera.
- **Respuestas de tu API**: un servidor comprometido, un proxy o simplemente una versión vieja del backend pueden devolver algo distinto de lo que esperas.
- **Archivos importados y portapapeles**: contenido que el usuario trae de fuera.

La validación del cliente mejora la experiencia y reduce la superficie de ataque, pero **la validación autoritativa vive en el servidor**: la app puede ser modificada, el servidor no. Valida en ambos lados y nunca confíes en que el cliente lo hizo.

### Validar con esquemas

Un esquema describe la forma exacta que aceptas y rechaza todo lo demás. Con `zod` ([https://zod.dev](https://zod.dev)), el esquema es también el tipo de TypeScript, así que no hay dos definiciones que puedan desalinearse:

```ts
import { z } from "zod";

export const noteInputSchema = z.object({
  title: z.string().trim().min(1).max(80),
  body: z.string().max(10_000),
  tag: z.enum(["work", "personal", "ideas"]),
});

export type NoteInput = z.infer<typeof noteInputSchema>;

export function parseNoteInput(raw: unknown): NoteInput | null {
  const result = noteInputSchema.safeParse(raw);
  return result.success ? result.data : null;
}
```

Tres reglas para escribir buenos esquemas:

1. **Listas permitidas, no prohibidas.** `z.enum([...])` acepta solo tres etiquetas; intentar prohibir "caracteres peligrosos" siempre deja alguno fuera.
2. **Límites de longitud en todo texto.** Sin `max`, un cuerpo de nota de 50 MB llega a la base de datos y a la red.
3. **`safeParse` en las fronteras, tipos dentro.** Una vez validado, el resto del código recibe `NoteInput` y no vuelve a comprobar nada.

El mismo esquema sirve para la respuesta de tu API: `noteSchema.array().safeParse(await res.json())` convierte una respuesta inesperada en un error controlado en lugar de en una pantalla en blanco.

### Cuando el texto se convierte en código: inyección

El caso clásico de MASVS-CODE-4 es la inyección SQL. Ocurre cuando construyes una consulta pegando texto del usuario, porque la base de datos no distingue qué parte escribiste tú y qué parte escribió él. Este es el patrón que **no** debes usar, con `expo-sqlite`:

```ts
// WRONG: the title becomes part of the SQL statement
await db.execAsync(`INSERT INTO notes (title) VALUES ('${title}')`);
```

Si el título contiene una comilla y algo más, la sentencia resultante ya no es la que escribiste:

```sql
-- title typed by the user:  x'); DELETE FROM notes; --
INSERT INTO notes (title) VALUES ('x'); DELETE FROM notes; --');
```

La solución no es "escapar comillas": es **no mezclar nunca datos con código**. Las consultas parametrizadas envían la sentencia y los valores por separado, y el motor garantiza que un valor es siempre un valor:

```ts
// RIGHT: placeholders keep data and SQL apart
await db.runAsync("INSERT INTO notes (title, body, tag) VALUES (?, ?, ?)", [
  input.title,
  input.body,
  input.tag,
]);
```

Con `?` como marcador, el título puede contener comillas, punto y coma o lo que sea: se guarda tal cual. Revisa en tu proyecto toda llamada a `execAsync`, `runAsync` o `getAllAsync` y confirma que la cadena SQL es un literal sin interpolación.

### Otras entradas que se olvidan

- **Deep links.** `notes://note/{id}`: valida que `id` tenga el formato que esperas (por ejemplo, un UUID) y que la nota pertenezca al usuario con sesión antes de mostrarla. Un deep link no es una prueba de identidad.
- **Nombres de archivo.** Si guardas adjuntos con el nombre que trae el usuario, `../../` puede escribir fuera del directorio previsto. Genera tú el nombre y guarda el original como dato.
- **HTML en WebView.** Si alguna vez muestras contenido del usuario en un WebView, es MASVS-PLATFORM-2: el texto debe codificarse como HTML, no insertarse crudo.

<Callout kind="tip">
  Regla corta para revisar código: si ves una plantilla de cadena con `${...}` que forma una consulta SQL, una ruta de archivo o HTML, es un hallazgo. Si ves un valor que cruza una frontera sin pasar por `safeParse`, también.
</Callout>

const noteSchema = z.object({
  title: z.string().trim().min(1, "Title is required").max(80, "Max 80 characters"),

    if (parsed.success) {
      setResult(["OK: " + JSON.stringify(parsed.data)]);

    }

      <Text style={styles.title}>New note</Text>
      <TextInput style={styles.input} placeholder="Title" value={title} onChangeText={setTitle} />
      <TextInput style={styles.input} placeholder="Email" value={email} onChangeText={setEmail} autoCapitalize="none" />
      <TextInput style={styles.input} placeholder="Tag: work | personal | ideas" value={tag} onChangeText={setTag} autoCapitalize="none" />
      <Pressable style={styles.button} onPress={onSubmit}>
        <Text style={styles.buttonText}>Validate and save</Text>
      </Pressable>
      {result.map((line, i) => (
        <Text key={i} style={line.startsWith("OK") ? styles.ok : styles.error}>{line}</Text>
      ))}
    </View>
  );
}

const styles = StyleSheet.create({

  buttonText: { color: "white", fontWeight: "600" },

## Errores comunes

**Validar solo en el cliente.** La app rechaza títulos vacíos, pero el endpoint acepta cualquier cosa porque "la app ya valida". Ocurre por olvidar que la app puede modificarse o sustituirse por un script. Se detecta enviando una petición directa al endpoint con `curl` y un cuerpo inválido: si responde 200, el servidor no valida.

**Construir SQL con plantillas de cadena.** Una plantilla con el título interpolado dentro de `execAsync` funciona en todas las pruebas hasta que un usuario escribe una comilla. Ocurre porque es más corto de escribir. Se detecta buscando el símbolo de dólar seguido de llave dentro de cadenas que contengan `SELECT`, `INSERT`, `UPDATE` o `DELETE`.

**Prohibir caracteres en lugar de permitir formatos.** Se filtra `'` y `;` del título, y el siguiente ataque usa otro carácter. Ocurre por pensar la validación como lista negra. Se detecta cuando la validación es una lista de `replace`; la solución es describir el formato aceptado (longitud, enum, expresión regular) y usar consultas parametrizadas.

**Confiar en la respuesta de la propia API.** `const notes = await res.json()` se usa directamente y la app se cae cuando el backend cambia un campo. Ocurre porque la API "es nuestra". Se detecta cuando un error de red o de versión produce una excepción dentro de un componente en lugar de un mensaje controlado.
