## Objetivo

Al terminar este proyecto tendrás el repositorio de la app de notas verificado automáticamente: lint, tipos, al menos cinco pruebas unitarias y un flujo E2E, con un workflow de GitHub Actions en verde en cada pull request.

**Prerrequisitos:** `06-calidad-ci/06-github-actions`

## Concepto

Un edificio nuevo no se entrega cuando las paredes están pintadas, sino cuando pasa la inspección final: el inspector recorre una lista fija (instalación eléctrica, salidas de emergencia, agua, gas) y firma solo si todo cumple. La lista no depende del humor del inspector ni de lo bonito que se vea el edificio. Este proyecto es la inspección final de tu app de notas: una lista objetiva de verificaciones que una máquina ejecuta en cada cambio.

### Punto de partida

Trabajas sobre el repositorio que terminaste en [el proyecto de la etapa 5](/etapa/05-estado-datos-arquitectura/10-proyecto-app-con-api): la app de notas con capas de dominio, infraestructura e interfaz, el puerto `NotesRepository` y su adaptador de SQLite. No agregas funcionalidades nuevas. El objetivo es que cada funcionalidad existente quede protegida.

### Qué vas a construir

**1. Herramientas de calidad.** ESLint con `eslint-config-expo` y la integración de Prettier, `strict: true` en `tsconfig.json` y estos scripts en `package.json`:

```json
{
  "packageManager": "pnpm@10.18.0",
  "scripts": {
    "lint": "expo lint --max-warnings 0",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "typecheck": "tsc --noEmit",
    "test": "jest",
    "test:watch": "jest --watch"
  },
  "jest": {
    "preset": "jest-expo",
    "clearMocks": true
  }
}
```

Usa en `packageManager` la versión que muestra `pnpm --version` en tu máquina. Si tu proyecto todavía tiene `package-lock.json`, haz primero la migración a pnpm de la lección de GitHub Actions (`pnpm import`, borrar `package-lock.json` y confirmar `pnpm-lock.yaml`); sin ella, `pnpm install --frozen-lockfile` falla en CI porque no hay lockfile de pnpm.

**2. Pruebas unitarias.** Al menos cinco pruebas con Jest y React Native Testing Library, repartidas así como mínimo:

| Archivo | Qué prueba | Técnica |
| --- | --- | --- |
| `src/features/notes/ui/useNotes.test.ts` | El hook carga y agrega notas | `renderHook`, repositorio falso inyectado |
| `src/features/notes/ui/NotesScreen.test.tsx` | La pantalla muestra lo que devuelve el repositorio | `jest.mock` del adaptador de SQLite |
| `src/features/notes/ui/NoteComposer.test.tsx` | El usuario escribe, guarda y ve la nota | `userEvent`, `getByRole`, `getByText` |

Con las pruebas de las lecciones anteriores ya tienes seis o siete. Si tu app tiene reglas de dominio propias, por ejemplo validar un título o ordenar notas, agrega pruebas para ellas: son las más baratas de escribir y de mantener.

**3. Un flujo de Maestro.** `flows/add-note.yaml`, independiente, que empieza con `clearState: true`, crea una nota y comprueba que aparece. Se ejecuta en tu máquina antes de pedir revisión.

**4. El workflow de CI.** `.github/workflows/ci.yml` que se dispara en cada pull request y en cada push a `main`, instala con pnpm y caché, y ejecuta lint, formato, tipos y pruebas. Una regla de GitHub exige que el check pase para integrar en `main`.

**5. La insignia.** El `README.md` empieza con la insignia de estado del workflow.

### Cómo trabajar

Haz el proyecto como lo harías en un equipo: una rama y una PR por paso. Por ejemplo, `chore: configure eslint and prettier`, `test(notes): cover useNotes hook`, `test(notes): add maestro flow for adding a note`, `ci: run lint, typecheck and tests on pull requests`. Así cada PR es pequeña y, desde que el workflow existe, cada PR siguiente ya se verifica sola.

Un orden que funciona:

1. Configura ESLint y Prettier y ejecuta `pnpm format` una vez. Integra ese cambio solo, sin mezclar lógica: es un diff grande pero mecánico.
2. Activa `strict` y corrige los errores de `pnpm typecheck` uno por uno. No uses `any` ni `// @ts-ignore` para salir del paso: cada error es una pregunta sobre qué pasa si el valor es `null` o `undefined`.
3. Agrega el workflow de CI lo antes posible, aunque solo ejecute lint. Cada verificación que agregues después ya correrá en la PR.
4. Escribe las pruebas unitarias, empezando por el hook, que no depende de la interfaz.
5. Escribe el flujo de Maestro al final, cuando el resto ya esté estable.

### Qué significa terminado

El proyecto está terminado cuando todo esto es verdad al mismo tiempo, en una copia recién clonada del repositorio:

- `pnpm lint`, `pnpm format:check` y `pnpm typecheck` terminan sin errores ni advertencias.
- `pnpm test` ejecuta al menos cinco pruebas y todas pasan.
- `maestro test flows/` pasa en un emulador con la app instalada.
- La última PR integrada muestra el check de CI en verde y `main` tiene una regla que lo exige.
- El `README.md` muestra la insignia en verde.

Para comprobar lo de "copia recién clonada", clona el repositorio en otra carpeta, ejecuta `pnpm install --frozen-lockfile` y los scripts. Si algo falla ahí, también fallará en CI.

Referencias: https://docs.github.com/es/actions, https://docs.expo.dev/develop/unit-testing/ y https://docs.maestro.dev/

## Errores comunes

**Silenciar herramientas para llegar al verde.** El pipeline pasa, pero el código tiene diez `// eslint-disable`, varios `as any` y una prueba marcada con `test.skip`. Ocurre por tratar el color del check como el objetivo en lugar de la calidad que representa. Se detecta buscando esos patrones en el repositorio antes de cerrar el proyecto; cada uno debe tener una justificación escrita o desaparecer.

**Pruebas que pasan aunque el código esté roto.** Tienes siete pruebas en verde, pero una de ellas prueba un mock y otra no tiene ningún `expect`. Ocurre al escribir pruebas para cumplir la cuota. Se detecta rompiendo a propósito la funcionalidad, por ejemplo haciendo que `addNote` no guarde nada: si ninguna prueba falla, la suite no protege esa funcionalidad.

**Workflow que solo funciona en la rama donde se creó.** El check aparece en la PR que agregó `ci.yml`, pero no en las siguientes o no se puede exigir en la regla de `main`. Ocurre cuando el workflow se dispara solo con `push` a una rama concreta o cuando la PR que lo agrega todavía no se integró. Se detecta abriendo una PR nueva después de integrar el workflow y comprobando que el check aparece.
