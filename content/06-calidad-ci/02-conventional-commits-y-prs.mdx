## Objetivo

Al terminar esta lección podrás escribir mensajes de commit con el formato Conventional Commits y abrir una pull request con una descripción que facilite la revisión.

**Prerrequisitos:** `06-calidad-ci/01-git-avanzado`

## Concepto

Piensa en las etiquetas de un archivo de oficina. Si cada carpeta dice "Cosas" o "Varios", encontrar un contrato de hace dos años exige abrirlas todas. Si cada una dice "Factura · Proveedor · 2025-03", lo encuentras en segundos y además puedes ordenar el archivo automáticamente. Un mensaje de commit es la etiqueta de un cambio. **Conventional Commits** es un acuerdo sobre cómo escribir esa etiqueta para que personas y herramientas la entiendan.

### El formato

```text
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

La primera línea, llamada **header**, es la parte obligatoria:

- **type**: qué clase de cambio es. Los dos tipos que define la especificación son `feat` (nueva funcionalidad) y `fix` (corrección de un bug). La convención más extendida agrega `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` y `revert`.
- **scope** (opcional): la parte del proyecto afectada, entre paréntesis. En la app de notas: `notes`, `quotes`, `auth`.
- **description**: qué hace el cambio, en imperativo y en minúscula: "add search", no "Added search" ni "adds search".

Ejemplos reales:

```text
feat(notes): add search by title
fix(quotes): retry when the API returns 503
test(notes): cover empty state
ci: run typecheck on pull requests
```

### Cambios incompatibles

Si un cambio rompe la compatibilidad, se marca con `!` antes de los dos puntos o con un footer `BREAKING CHANGE:`:

```text
feat(storage)!: migrate notes table to v2 schema

BREAKING CHANGE: notes saved with v1 must be migrated on first launch.
```

### Por qué vale la pena

Conventional Commits se alinea con el **versionado semántico**: un `fix` sugiere subir la versión de parche (1.4.2 a 1.4.3), un `feat` la versión menor (1.4.2 a 1.5.0) y un cambio con `!` la versión mayor (1.4.2 a 2.0.0). Con historias bien etiquetadas, herramientas externas pueden generar el changelog y calcular la versión siguiente sin intervención humana. Aunque no uses esas herramientas, `git log --oneline` se vuelve legible: sabes qué commit introdujo una funcionalidad y cuál solo cambió documentación.

Especificación oficial en español: https://www.conventionalcommits.org/es/v1.0.0/

### Un commit, una idea

El formato te obliga a elegir un solo tipo. Si no puedes, probablemente el commit mezcla dos cambios: por ejemplo, una funcionalidad nueva y una refactorización. Sepáralos. Commits atómicos significan revisiones más simples y un `git revert` que deshace exactamente lo que quieres.

### Pull requests

Una **pull request** (PR) propone integrar tu rama en `main` y abre un espacio para revisión. Tres reglas prácticas:

1. **Pequeña.** Menos de 400 líneas cambiadas es una buena meta. Una PR de 2000 líneas recibe un "se ve bien" sin revisión real.
2. **Descriptiva.** Qué cambia, por qué y cómo probarlo. La persona que revisa no estuvo en tu cabeza.
3. **Verde.** Antes de pedir revisión, lint, tipos y pruebas deben pasar en tu máquina.

Con la CLI de GitHub (`gh`) puedes abrirla desde la terminal:

```bash
gh pr create --title "feat(notes): add search by title" --body-file pr.md
```

Para que todas las PR tengan la misma estructura, crea `.github/pull_request_template.md`. GitHub lo usa como texto inicial de cada PR nueva:

```markdown
## What

## Why

## How to test

- [ ] `pnpm lint` passes
- [ ] `pnpm typecheck` passes
- [ ] `pnpm test` passes
- [ ] Screenshots attached for UI changes
```

El título de la PR también sigue Conventional Commits. Si el repositorio integra con "squash and merge", ese título se convierte en el único commit que queda en `main`.

  type: string;
  scope: string | null;
  breaking: boolean;
  description: string;

const HEADER = /^([a-z]+)(?:[(]([a-z0-9-]+)[)])?(!)?: (.+)$/;

  const match = HEADER.exec(header);
  if (match === null) return null;
  return {
    type: match[1],
    scope: match[2] ?? null,
    breaking: match[3] === "!",

## Errores comunes

**Mensajes que describen el proceso, no el cambio.** Aparecen como `fix: stuff`, `wip` o `feat: changes from review`. Ocurren al hacer commit por costumbre al final del día. Se detectan leyendo `git log --oneline`: si no puedes saber qué hace cada commit sin abrirlo, los mensajes no cumplen su función.

**Usar `feat` para todo.** Una refactorización o una actualización de documentación etiquetada como `feat` hace que la herramienta de versionado suba la versión menor sin motivo. Pasa porque `feat` parece "trabajo importante". Se detecta preguntando: ¿el usuario final ve algo nuevo? Si no, no es `feat`.

**PRs gigantes.** Una PR con cambios de formato, una migración y una funcionalidad nueva en 1500 líneas. Ocurre por no separar el trabajo en ramas pequeñas. Se detecta porque el resumen de GitHub muestra decenas de archivos y la revisión tarda días.
