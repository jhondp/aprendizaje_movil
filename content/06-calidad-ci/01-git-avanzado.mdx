## Objetivo

Al terminar esta lección podrás crear una rama de funcionalidad, actualizarla con `git rebase` sobre `main` y resolver un conflicto de forma segura.

**Prerrequisitos:** `06-calidad-ci/00-eslint-prettier-y-ts-strict`

## Concepto

Imagina que escribes un capítulo de un libro en tu propio cuaderno mientras la editorial sigue corrigiendo la versión oficial. Cuando terminas, tienes dos opciones: entregar tu cuaderno junto con una nota que diga "esto se escribió en paralelo" o **copiar tus páginas encima de la última edición oficial**, como si hubieras empezado a escribir hoy. La primera opción es un **merge**; la segunda es un **rebase**. Si la editorial cambió la misma frase que tú, tendrás que decidir qué versión queda: eso es un **conflicto**.

### Ramas de funcionalidad

Una rama es un marcador móvil que apunta a un commit. Crear una rama es barato y no copia archivos. La práctica habitual es no trabajar nunca directamente sobre `main`: cada cambio vive en su propia rama hasta que se revisa.

```bash
git switch main
git pull
git switch -c feat/notes-search
```

`git switch -c` crea la rama y te mueve a ella en un solo paso. El nombre describe el propósito del cambio; muchos equipos usan un prefijo como `feat/` o `fix/`.

### Merge y rebase

Mientras trabajas, otras personas integran cambios en `main`. Tu rama queda "atrasada". Hay dos formas de traer esos cambios.

**Merge** crea un commit nuevo que une las dos historias. No reescribe nada, pero la historia queda con bifurcaciones:

```bash
git switch feat/notes-search
git merge main
```

**Rebase** toma tus commits y los vuelve a aplicar, uno por uno, encima del último commit de `main`. El resultado es una historia lineal, como si hubieras empezado tu rama hoy:

```bash
git fetch origin
git rebase origin/main
```

Después de un rebase tus commits tienen identificadores nuevos, porque su "padre" cambió. Si ya habías publicado la rama, el servidor rechaza un `git push` normal. Debes usar:

```bash
git push --force-with-lease
```

`--force-with-lease` solo sobrescribe la rama remota si nadie más subió commits desde tu última descarga. `--force` sobrescribe sin preguntar y puede borrar el trabajo de otra persona.

La regla de oro: **haz rebase solo de ramas que son tuyas**. Nunca hagas rebase de `main` ni de una rama compartida.

### Anatomía de un conflicto

Un conflicto ocurre cuando dos commits modifican las mismas líneas de un archivo. Git no adivina: detiene la operación y marca el archivo así:

```text
<<<<<<< HEAD
const PAGE_SIZE = 20;
=======
const PAGE_SIZE = 50;
>>>>>>> 3f2a91c (feat(notes): load more notes per page)
```

- Entre `<<<<<<<` y `=======` está la versión de la base sobre la que se aplica tu commit. Durante un rebase, `HEAD` es `main`, no tu rama. Durante un merge, `HEAD` es tu rama. Esta inversión confunde a casi todo el mundo la primera vez.
- Entre `=======` y `>>>>>>>` está la versión que llega: durante un rebase, tu commit.

Para resolverlo, editas el archivo hasta dejar el código correcto, borras los tres marcadores y le avisas a Git:

```bash
git add src/features/notes/constants.ts
git rebase --continue
```

Si te pierdes, `git rebase --abort` devuelve la rama exactamente al estado anterior al rebase. Es tu botón de emergencia.

### Ver la historia

Para entender dónde estás, el comando más útil es:

```bash
git log --oneline --graph --all
```

Muestra cada commit en una línea y dibuja las ramas. Úsalo antes y después de un rebase para ver qué cambió.

### Deshacer con red de seguridad

Git casi nunca pierde commits. `git reflog` lista cada posición por la que pasó `HEAD`, incluso las que ya no aparecen en ninguna rama. Si un rebase salió mal y ya lo terminaste, busca en el reflog el commit anterior y crea una rama desde ahí.

Guía oficial en español: https://git-scm.com/book/es/v2/Ramificaciones-en-Git-Procedimientos-B%C3%A1sicos-para-Ramificar-y-Fusionar

## Errores comunes

**Hacer rebase de una rama compartida.** Otra persona descarga la rama, tú haces rebase y `push --force`, y su historia deja de coincidir con la tuya: aparecen commits duplicados al integrar. Ocurre por aplicar el rebase fuera de las ramas propias. Se detecta cuando `git pull` en la otra máquina crea commits repetidos con el mismo mensaje.

**Confundir los lados del conflicto durante un rebase.** Borras el bloque de `HEAD` pensando que es tu versión y en realidad borraste la de `main`. Pasa porque en un rebase `HEAD` es la base, no tu rama. Se detecta revisando el diff con `git diff origin/main` antes de hacer push.

**Dejar marcadores en el código.** El archivo compila con errores de sintaxis o, peor, un `=======` queda dentro de una cadena. Ocurre al hacer `git add` sin revisar el archivo completo. Se detecta buscando los marcadores con `git diff --check`, que los reporta como error.
