## Objetivo

Al terminar esta lección podrás escribir un workflow de GitHub Actions que ejecuta lint, verificación de tipos y pruebas en cada pull request, y leer su resultado desde la terminal.

**Prerrequisitos:** `06-calidad-ci/05-e2e-con-maestro`

## Concepto

En una fábrica de pan, cada lote pasa por un control de calidad antes de salir hacia las tiendas: alguien pesa una muestra, revisa la cocción y la etiqueta. No depende de que el panadero se acuerde; ocurre siempre, con cada lote, y un lote que no pasa no sale. La **integración continua** (CI) es ese control para tu código: cada vez que alguien propone un cambio, un servidor limpio descarga el repositorio y ejecuta las mismas verificaciones que tú ejecutas en tu máquina. Si algo falla, el cambio no entra en `main`.

### Por qué no basta con tu máquina

Tu computadora tiene dependencias instaladas hace meses, variables de entorno que olvidaste y archivos que no están en Git. Un servidor de CI empieza siempre desde cero, así que detecta el clásico "en mi máquina funciona". Además, las verificaciones dejan de depender de la disciplina de cada persona: aunque alguien olvide ejecutar `pnpm test`, la PR lo muestra en rojo.

### Conceptos de GitHub Actions

GitHub Actions es el servicio de CI integrado en GitHub. Documentación oficial en español: https://docs.github.com/es/actions

- **Workflow**: un archivo YAML en `.github/workflows/`. Un repositorio puede tener varios.
- **Evento**: lo que dispara el workflow, declarado en `on`. Por ejemplo, `pull_request` o `push` a una rama.
- **Job**: un conjunto de pasos que se ejecuta en una máquina virtual nueva, llamada **runner**. Los jobs de un workflow corren en paralelo salvo que declares dependencias.
- **Step**: un paso dentro del job. Puede ser un comando de terminal (`run`) o una **action** reutilizable publicada por otra persona (`uses`).

### El workflow completo

Este es el archivo completo para la app de notas. Asume que `package.json` tiene los scripts `lint`, `format:check`, `typecheck` y `test` que definiste en lecciones anteriores:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    name: Lint, typecheck and test
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Check out the repository
        uses: actions/checkout@v4

      - name: Install pnpm
        uses: pnpm/action-setup@v4

      - name: Set up Node.js with the pnpm cache
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Lint
        run: pnpm lint

      - name: Check formatting
        run: pnpm format:check

      - name: Typecheck
        run: pnpm typecheck

      - name: Unit tests
        run: pnpm test --ci
```

Recorre el archivo de arriba abajo:

- `on` dispara el workflow en cada pull request y en cada push a `main`. Así verificas la propuesta y también el resultado después de integrarla.
- `concurrency` cancela la ejecución anterior de la misma rama cuando subes un commit nuevo. Sin esto, tres pushes seguidos generan tres ejecuciones y solo te importa la última.
- `timeout-minutes` corta el job si se queda colgado, por ejemplo por un `jest --watchAll` olvidado. El límite por defecto es de seis horas.
- `actions/checkout` descarga el repositorio en el runner.
- `pnpm/action-setup` instala pnpm. Lee la versión exacta del campo `packageManager` de tu `package.json`, por ejemplo `"packageManager": "pnpm@10.18.0"`. Si ese campo no existe, agrégalo con la versión que muestra `pnpm --version`.
- `actions/setup-node` instala Node y, con `cache: pnpm`, guarda el almacén de paquetes de pnpm entre ejecuciones. La clave del caché incluye el hash de `pnpm-lock.yaml`: mientras el lockfile no cambie, la instalación reutiliza lo descargado y tarda segundos en lugar de minutos.
- `pnpm install --frozen-lockfile` falla si `package.json` y `pnpm-lock.yaml` no coinciden. En CI nunca quieres que el lockfile se actualice solo: quieres instalar exactamente lo que se revisó.
- Los cuatro pasos finales ejecutan tus scripts. Si cualquiera termina con un código distinto de cero, el job se detiene y se marca en rojo. La opción `--ci` de Jest desactiva la escritura de snapshots nuevos, para que una prueba sin snapshot falle en lugar de crearlo en silencio.

El orden importa por velocidad: lint y formato fallan en segundos, así que van antes que las pruebas.

### Checks en la pull request

Cuando abres una PR, GitHub muestra el job "Lint, typecheck and test" en la sección de checks, con un punto amarillo mientras corre y una marca verde o una cruz roja al terminar. Desde la terminal puedes seguir lo mismo con `gh`:

```bash
gh pr checks
gh run watch
gh run view --log-failed
```

`gh run view --log-failed` muestra solo el log de los pasos fallidos, que es casi siempre lo único que necesitas leer.

### Proteger main

Un check en rojo es solo un aviso si alguien puede integrar la PR igual. En GitHub, ve a **Settings → Branches** (o **Rules → Rulesets**) y crea una regla para `main` que exija que el check "Lint, typecheck and test" pase antes de integrar. Desde ese momento, el botón de merge queda bloqueado mientras el pipeline esté en rojo.

### La insignia de estado

GitHub genera una imagen que muestra el estado del último run de un workflow. Agrégala al inicio del `README.md`:

```markdown
![CI](https://github.com/ana/notes/actions/workflows/ci.yml/badge.svg)
```

Cambia `ana/notes` por tu usuario y repositorio. Quien visite el repositorio ve de inmediato si `main` está sano.

## Errores comunes

**Instalar sin `--frozen-lockfile`.** El CI instala versiones distintas de las que probaste y aparece un fallo que no puedes reproducir, o peor, pasa algo que en tu máquina falla. Ocurre porque `pnpm install` puede actualizar el lockfile. Se detecta revisando el log de instalación: con `--frozen-lockfile`, un lockfile desactualizado detiene el job con un error explícito.

**Versión de pnpm sin declarar.** El paso `pnpm/action-setup` falla con un mensaje que pide una versión. Ocurre porque no hay campo `packageManager` en `package.json` ni `version` en el paso. Se detecta en el primer run; la solución es declarar `packageManager` para que tu máquina y el CI usen la misma versión.

**Checks que nadie exige.** El pipeline está en rojo desde hace una semana y las PR se integran igual. Ocurre porque el workflow existe pero no hay regla de protección sobre `main`. Se detecta abriendo una PR en rojo: si el botón de merge está disponible, el check es decorativo.
