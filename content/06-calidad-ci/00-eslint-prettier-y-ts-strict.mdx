## Objetivo

Al terminar esta lección podrás configurar ESLint, Prettier y TypeScript strict en un proyecto de Expo y ejecutar las tres verificaciones desde la terminal.

**Prerrequisitos:** `05-estado-datos-arquitectura/10-proyecto-app-con-api`

## Concepto

Piensa en cómo se publica un libro. Antes de imprimirlo pasan tres revisiones distintas: el **corrector de estilo** detecta frases confusas y errores que cambian el sentido; el **maquetador** decide márgenes, tipografía y sangrías para que todas las páginas se vean iguales; y el **verificador de datos** comprueba que cada fecha y cada cifra sea coherente con el resto del libro. Ninguno reemplaza al otro. En un proyecto de JavaScript, esas tres revisiones son ESLint, Prettier y TypeScript.

### ESLint: el corrector de estilo

ESLint lee tu código sin ejecutarlo y aplica **reglas**. Cada regla describe un patrón sospechoso: una variable que nunca se usa, un `useEffect` al que le falta una dependencia, una comparación con `==` que puede sorprenderte. Muchas de esas reglas no son de gusto personal: señalan bugs reales antes de que llegues a abrir el simulador.

Expo trae una configuración lista. Un solo comando instala las dependencias y crea el archivo de configuración:

```bash
npx expo lint
```

Desde el SDK 53, Expo genera un archivo `eslint.config.js` con el formato "flat config" de ESLint 9:

```js
// eslint.config.js
const { defineConfig } = require("eslint/config");
const expoConfig = require("eslint-config-expo/flat");

module.exports = defineConfig([
  expoConfig,
  {
    ignores: ["dist/*"],
  },
]);
```

`eslint-config-expo` ya incluye las reglas de React, de los hooks (`react-hooks/rules-of-hooks` y `react-hooks/exhaustive-deps`) y de TypeScript. Documentación oficial: https://docs.expo.dev/guides/using-eslint/

### Prettier: el maquetador

Prettier no busca errores: reescribe tu código con un formato único. Comillas, punto y coma, ancho de línea y sangrías quedan decididos por una herramienta, no por discusiones en cada pull request. Se instala junto con dos paquetes que lo integran con ESLint:

```bash
npx expo install prettier eslint-config-prettier eslint-plugin-prettier --dev
```

Luego agregas su configuración recomendada a `eslint.config.js`. Así ESLint desactiva las reglas de formato que chocarían con Prettier y reporta las diferencias de formato como problemas:

```js
// eslint.config.js
const { defineConfig } = require("eslint/config");
const expoConfig = require("eslint-config-expo/flat");
const eslintPluginPrettierRecommended = require("eslint-plugin-prettier/recommended");

module.exports = defineConfig([
  expoConfig,
  eslintPluginPrettierRecommended,
  {
    ignores: ["dist/*"],
  },
]);
```

Si quieres ajustar alguna opción, crea un archivo `.prettierrc` en la raíz del proyecto. Cambia pocas cosas: el valor de Prettier está en que nadie discute el formato.

```json
{
  "singleQuote": true,
  "printWidth": 100
}
```

Documentación oficial: https://prettier.io/docs/en/

### TypeScript strict: el verificador de datos

Ya escribes TypeScript, pero Metro, el bundler de Expo, **no revisa tipos**: elimina las anotaciones y ejecuta el JavaScript resultante. Si un tipo está mal, la app arranca igual. Por eso necesitas ejecutar el compilador aparte, sin generar archivos:

```bash
npx tsc --noEmit
```

El modo `strict` activa las comprobaciones que más errores atrapan, como prohibir parámetros con tipo `any` implícito o avisar cuando un valor puede ser `null`. En un proyecto de Expo, `tsconfig.json` queda así:

```json
{
  "extends": "expo/tsconfig.base",
  "compilerOptions": {
    "strict": true
  }
}
```

### Scripts en package.json

Para no memorizar comandos, declara un script por verificación. Más adelante el pipeline de integración continua ejecutará exactamente estos mismos scripts:

```json
{
  "scripts": {
    "lint": "expo lint --max-warnings 0",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "typecheck": "tsc --noEmit"
  }
}
```

La opción `--max-warnings 0` convierte cualquier advertencia en un fallo. Sin ella, ESLint termina con éxito aunque reporte veinte advertencias, y las advertencias que nadie arregla se acumulan hasta que todos las ignoran.

### El orden importa poco, la constancia mucho

Las tres herramientas son rápidas y complementarias. Lo importante es ejecutarlas siempre, no solo cuando te acuerdas. Configura tu editor para formatear al guardar y para mostrar los errores de ESLint en línea: así corriges cada problema en el momento en que lo escribes, cuando todavía tienes el contexto en la cabeza.

## Errores comunes

**Confiar en que Metro revisa tipos.** La app arranca sin errores aunque `tsc` reporte diez. Ocurre porque Metro solo transpila y descarta los tipos. Se detecta ejecutando `npx tsc --noEmit`: si nunca lo ejecutas, tus tipos son decoración.

**Silenciar `exhaustive-deps` con un comentario.** Aparece como `// eslint-disable-next-line react-hooks/exhaustive-deps` encima de un efecto. Suele ocurrir porque agregar la dependencia provoca un bucle, y el comentario "lo arregla". En realidad oculta un valor desactualizado. Se detecta buscando `eslint-disable` en el repositorio; la solución habitual es calcular el valor en el render o mover la lógica dentro del efecto.

**ESLint y Prettier peleando por el formato.** Guardas el archivo, Prettier lo formatea y ESLint marca error en la misma línea. Pasa cuando falta `eslint-config-prettier` o la configuración recomendada no está incluida. Se detecta porque `prettier --check` pasa pero `expo lint` reporta reglas de formato como `indent` o `quotes`.
