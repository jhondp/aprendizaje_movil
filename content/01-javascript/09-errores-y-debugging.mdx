## Objetivo

Al terminar esta lección podrás atrapar errores con `try`/`catch`, lanzar un error propio con `throw new Error`, y leer un stack trace para encontrar dónde ocurrió el problema.

**Prerrequisitos:** `01-javascript/08-scope-y-closures`

## Concepto

Hasta ahora, cuando algo salía mal en tus ejemplos, JavaScript detenía el programa por completo. Un error sin control es como una alarma de incendio que corta la electricidad de todo el edificio: nadie puede seguir trabajando, aunque el problema esté en una sola oficina. `try`/`catch` es el equivalente a contener el problema en esa oficina, sin apagar el resto del edificio.

### try y catch

`try` envuelve un bloque de código que podría fallar. Si algo dentro de `try` lanza un error, la ejecución salta inmediatamente al bloque `catch`, que recibe el error como parámetro, en lugar de detener todo el programa.

```js
try {
  const result = 10 / 0;
  console.log(result); // Infinity, no es un error en JavaScript

  JSON.parse("esto no es JSON válido");
  console.log("esto nunca se imprime");
} catch (error) {
  console.log("Algo falló:", error.message);
}

console.log("El programa sigue ejecutándose");
```

`10 / 0` no lanza un error en JavaScript, produce `Infinity`. `JSON.parse` con un texto inválido sí lanza un error, así que la ejecución salta al `catch` y la línea siguiente dentro del `try` nunca se alcanza. Después del `catch`, el programa continúa con normalidad.

### throw: lanzar tus propios errores

A veces tú decides que una situación es un error, aunque JavaScript no lo detecte solo. `throw new Error("mensaje")` crea y lanza un error con un mensaje descriptivo.

```js
function divide(a, b) {
  if (b === 0) {
    throw new Error("No se puede dividir entre cero");
  }
  return a / b;
}

try {
  console.log(divide(10, 2)); // 5
  console.log(divide(10, 0)); // nunca se imprime
} catch (error) {
  console.log("Error capturado:", error.message);
}
```

`throw` detiene inmediatamente la función donde se ejecuta, igual que `return`, pero en lugar de entregar un valor, propaga un error hacia arriba hasta que algún `catch` lo atrape.

### Leer un stack trace

Cuando un error no se atrapa, la consola muestra un stack trace: el mensaje del error, seguido de la lista de funciones que estaban activas en el momento del error, de la más reciente a la más antigua. Por ejemplo:

```
Error: No se puede dividir entre cero
    at divide (app.js:3)
    at main (app.js:10)
```

La primera línea es el mensaje. La segunda dice que el error ocurrió dentro de la función `divide`, en la línea 3. La tercera dice que `divide` fue llamada desde `main`, en la línea 10. Leer un stack trace de arriba hacia abajo te lleva del síntoma (dónde se lanzó el error) hasta la causa (quién lo provocó).

Puedes revisar la referencia completa de `try...catch` y de `Error` en MDN: https://developer.mozilla.org/es/docs/Web/JavaScript/Reference/Statements/try...catch.

<Callout kind="tip">
  No uses try/catch para controlar el flujo normal de un programa, solo para casos verdaderamente excepcionales. Si algo puede evitarse con un if (como validar que b no sea 0 antes de dividir), un if es más claro que un try/catch.
</Callout>

## Errores comunes

**Usar try/catch para evitar leer el mensaje del error.** Escribir `catch (error) { console.log("algo falló"); }` sin mirar `error.message` esconde información valiosa para encontrar la causa real. Se detecta porque el problema tarda mucho en resolverse aunque el error ya esté "atrapado". Solución: siempre registrar `error.message`, al menos mientras depuras.

**Poner demasiado código dentro de un solo try.** Si el `try` envuelve diez líneas, el `catch` no sabe cuál de las diez falló. Se detecta porque el stack trace señala una línea, pero el bloque `try` es tan grande que no ayuda a entender el contexto. Solución: envolver solo la operación que realmente puede fallar.

**Leer el stack trace de abajo hacia arriba.** El stack trace muestra primero dónde se lanzó el error (la causa más inmediata) y después la cadena de llamadas que llevó hasta ahí. Empezar a leer desde la última línea en vez de la primera hace perder tiempo buscando el mensaje del error. Se detecta si, al depurar, no encuentras rápido qué línea del propio código provocó el problema.
