## Objetivo

Al terminar esta lección podrás separar una feature en dominio, puerto, caso de uso y adaptador, y cambiar el almacenamiento sin tocar las reglas de la app.

**Prerrequisitos:** `05-estado-datos-arquitectura/05-sqlite-y-securestore`

## Concepto

En la lección anterior escribiste funciones como `addNote(db, title)` que reciben la base SQLite directamente. Funciona, pero tiene un costo escondido: la regla "una nota necesita título" y la decisión "las notas viven en SQLite" quedaron mezcladas en el mismo lugar. Si mañana quieres probar la regla sin un dispositivo, o guardar las notas en una API, tienes que reescribir las dos cosas a la vez.

La arquitectura hexagonal, también llamada de puertos y adaptadores, propone separar esas dos preguntas. Alistair Cockburn la describió así: https://alistair.cockburn.us/hexagonal-architecture/

Piensa en un secador de pelo y un viaje. El secador (tu lógica) funciona igual en cualquier país. Lo que cambia es el enchufe de la pared. El secador define qué forma de clavija necesita (el puerto) y, en cada país, usas un adaptador que conecta esa clavija con el enchufe local. Nadie abre el secador para cambiarle el cable cuando viaja.

### Las piezas

- **Dominio**: los datos y las reglas del negocio. Qué es una nota, qué la hace válida. Son funciones puras de TypeScript.
- **Puerto**: un contrato que la aplicación necesita del mundo exterior, escrito como un tipo. "Necesito algo que guarde y liste notas."
- **Caso de uso**: una acción que el usuario puede hacer ("agregar una nota"). Usa el dominio y habla con el exterior solo a través de puertos.
- **Adaptador**: una implementación concreta de un puerto. Un repositorio en memoria, uno con SQLite, uno con una API.
- **Interfaz (UI)**: las pantallas de React Native. Llaman a casos de uso; no saben qué adaptador hay detrás.

La regla que sostiene todo es la dirección de las dependencias: **el dominio no importa nada de React ni de Expo**. El caso de uso importa el dominio y el puerto. El adaptador importa el puerto y la librería concreta. Las flechas siempre apuntan hacia el centro.

### Una feature, tres archivos

No necesitas veinte carpetas para empezar. Con la feature de notas bastan tres archivos y la pantalla.

El dominio define la nota y su regla de validación:

```ts
// src/notes/note.ts
export type Note = { id: string; title: string; createdAt: string };

export function createNote(title: string, now: Date): Note {
  const clean = title.trim();
  if (clean.length === 0) throw new Error("El título es obligatorio");
  if (clean.length > 80) throw new Error("El título admite hasta 80 caracteres");
  return { id: String(now.getTime()), title: clean, createdAt: now.toISOString() };
}
```

La capa de aplicación declara el puerto y los casos de uso. Fíjate en que `now` llega como función: así un test puede fijar la fecha.

```ts
// src/notes/notesService.ts
import { createNote, type Note } from "./note";

export type NotesRepository = {
  list(): Promise<Note[]>;
  save(note: Note): Promise<void>;
};

export function makeAddNote(repository: NotesRepository, now: () => Date) {
  return async (title: string): Promise<Note> => {
    const note = createNote(title, now());
    await repository.save(note);
    return note;
  };
}

export function makeListNotes(repository: NotesRepository) {
  return (): Promise<Note[]> => repository.list();
}
```

El adaptador cumple el puerto. Este guarda en memoria; el de SQLite tendría la misma forma con `runAsync` y `getAllAsync` dentro.

```ts
// src/notes/inMemoryNotesRepository.ts
import type { Note } from "./note";
import type { NotesRepository } from "./notesService";

export function createInMemoryNotesRepository(): NotesRepository {
  let notes: Note[] = [];
  return {
    async list() {
      return [...notes].sort((a, b) => b.createdAt.localeCompare(a.createdAt));
    },
    async save(note) {
      notes = [...notes, note];
    },
  };
}
```

Falta un lugar que conecte todo, llamado **raíz de composición**. Es el único archivo que conoce el adaptador concreto:

```ts
// src/notes/notesModule.ts
import { createInMemoryNotesRepository } from "./inMemoryNotesRepository";
import { makeAddNote, makeListNotes } from "./notesService";

const repository = createInMemoryNotesRepository();

export const addNote = makeAddNote(repository, () => new Date());
export const listNotes = makeListNotes(repository);
```

La pantalla importa `addNote` y `listNotes` de ese módulo. Cambiar a SQLite significa escribir `createSqliteNotesRepository` y cambiar una línea en `notesModule.ts`. `note.ts`, `notesService.ts` y la pantalla quedan intactos.

### Qué ganas y qué pagas

Ganas tres cosas. Pruebas las reglas con funciones puras, sin emulador. Cambias de almacenamiento o de API sin reescribir la lógica. Y cada archivo responde a una sola pregunta, lo que facilita leer el código de otra persona.

Pagas con más archivos e indirección. Para una pantalla que solo muestra un texto fijo, esta separación es excesiva. Úsala cuando haya reglas que proteger o cuando sepas que el almacenamiento puede cambiar.

### Un ejemplo real

Esta misma plataforma de aprendizaje sigue la idea. Su código está en `src/` con estas carpetas:

```text
src/
├── domain/            # pure rules: notes, progress, spaced repetition
│   └── notes/
├── application/
│   ├── ports/         # Repositories.ts, Store.ts, Clock.ts
│   └── useCases/      # completeLesson.ts, gradeCard.ts
├── infrastructure/
│   └── storage/       # createPersistedStore.ts: the localStorage adapter
└── ui/                # React components
```

Los archivos de `src/domain/notes`, `src/domain/progress` y `src/domain/srs` no importan React. Hay una excepción consciente: `src/domain/course/types.ts` importa solo el tipo `ComponentType` de React para describir el componente de una lección, un compromiso pragmático que vale la pena conocer. `src/application/ports/Clock.ts` aplica la misma idea que `now: () => Date` de arriba: el reloj es un puerto, y los tests usan un reloj fijo en lugar del real.

function createNote(title, now) {

function createAsyncStorageNotesRepository(key) {
  const read = async () => {
    const raw = await AsyncStorage.getItem(key);
    try {
      return raw === null ? [] : JSON.parse(raw);

    },
  };
}

const listNotes = makeListNotes(repository);

## Errores comunes

**Importar React o Expo desde el dominio.** Se ve como un `note.ts` que hace `import { Alert } from "react-native"` para avisar de un título vacío, o que llama a `SQLite.openDatabaseAsync`. Pasa porque es cómodo resolverlo ahí mismo. El dominio deja de poder probarse sin un dispositivo y queda atado a una librería. Se detecta revisando los `import` de los archivos de dominio: solo deben apuntar a otros archivos de dominio. Solución: el dominio lanza un error y la pantalla decide cómo mostrarlo.

**Importar el adaptador dentro del caso de uso.** Se ve como `import { sqliteRepository } from "./sqliteNotesRepository"` en `notesService.ts`. Ocurre por saltarse la raíz de composición. El caso de uso vuelve a depender de SQLite y el puerto pierde sentido. Se detecta porque no puedes probar el caso de uso sin SQLite. Solución: el caso de uso recibe el repositorio como parámetro.

**Crear capas vacías por anticipado.** Se ve como un proyecto con veinte carpetas y archivos que solo reexportan otros. Pasa por copiar una plantilla empresarial antes de tener el problema. El código se vuelve difícil de navegar sin ganar nada. Se detecta cuando un cambio pequeño obliga a tocar cinco archivos que no tienen lógica. Solución: empieza con una feature y tres archivos, y separa más solo cuando duela.
