## Objetivo

Al terminar esta lección podrás organizar un proyecto de Expo en carpetas por feature con las capas `domain`, `application`, `infrastructure` y `ui`, y definir qué puede importar cada una.

**Prerrequisitos:** `05-estado-datos-arquitectura/06-arquitectura-hexagonal`

## Concepto

En la lección anterior separaste la feature de notas en dominio, puerto, caso de uso y adaptador. Queda una pregunta práctica: ¿dónde pongo esos archivos cuando la app tiene notas, frases, ajustes y perfil?

Piensa en el plano de una casa. Al verlo, sabes de inmediato que es una casa: ves cocina, dormitorios, baño. Nadie dibuja el plano agrupando "todas las paredes" en una hoja y "todas las puertas" en otra. Robert C. Martin llamó screaming architecture a esta idea: la estructura del proyecto debe "gritar" qué hace la app, no qué herramientas usa. Artículo original: https://blog.cleancoder.com/uncle-bob/2011/09/30/Screaming-Architecture.html

### Por capa o por feature

Hay dos formas comunes de ordenar carpetas. **Por capa** o tipo de archivo:

```text
src/
├── components/
├── hooks/
├── screens/
├── services/
└── stores/
```

Esta estructura grita "React". Para cambiar algo de las notas abres cinco carpetas, y nada impide que `services/` importe de `screens/`.

**Por feature**, cada carpeta es una capacidad de la app y adentro repite las capas de la lección anterior:

```text
src/
├── app/                  # Expo Router routes, thin
│   ├── _layout.tsx
│   └── index.tsx
├── features/
│   ├── notes/
│   │   ├── domain/
│   │   ├── application/
│   │   ├── infrastructure/
│   │   ├── ui/
│   │   └── index.ts      # public API of the feature
│   └── quotes/
└── shared/               # code with no feature: ui kit, utils
```

Al abrir `src/features` ves "notas" y "frases". Todo lo que cambia junto vive junto, y borrar una feature es borrar una carpeta.

### Las reglas de cada capa

Las carpetas solo sirven si las reglas de dependencias se respetan. Dentro de una feature:

| Capa | Contiene | Puede importar |
| --- | --- | --- |
| `domain` | Tipos y reglas puras | Nada de otras capas ni de React o Expo |
| `application` | Puertos y casos de uso | `domain` |
| `infrastructure` | Adaptadores: SQLite, `fetch`, AsyncStorage | `domain`, `application` y librerías externas |
| `ui` | Pantallas, componentes, hooks de React | `domain`, `application` |

Entre features, la regla es otra: una feature solo importa de otra a través de su `index.ts`. Así `quotes` puede usar el tipo `Note` exportado por `features/notes/index.ts` sin conocer sus carpetas internas.

### Rutas delgadas

Con Expo Router las rutas viven en `src/app/`, y la tentación es escribir toda la pantalla ahí. Mantén esos archivos delgados: importan una pantalla de la feature y la exportan.

```tsx
// src/app/index.tsx
import { NotesScreen } from "@/features/notes";

export default NotesScreen;
```

El alias `@/` apunta a `src/`; Expo lo configura en `tsconfig.json` con `"paths": { "@/*": ["./src/*"] }`. Documentación: https://docs.expo.dev/guides/typescript/#path-aliases

### Un contraejemplo honesto

Esta plataforma de aprendizaje está organizada primero por capa (`src/domain`, `src/application`, `src/infrastructure`, `src/ui`) y dentro de `src/domain` por tema (`notes`, `progress`, `srs`). Es una decisión razonable para una app pequeña con un solo equipo: las capas quedan muy visibles y los puertos se comparten. Cuando las features crecen y distintos equipos trabajan en ellas, agrupar primero por feature reduce los choques. Lo importante no es cuál eliges, sino que las reglas de dependencias sean las mismas y se revisen.

## Errores comunes

**Rutas gordas en `src/app`.** Se ve como `src/app/index.tsx` con doscientas líneas, `useQuery`, SQLite y estilos. Pasa porque Expo Router hace que ese archivo sea lo primero que se abre. La lógica queda atada a la navegación y no se puede reutilizar. Se detecta porque los archivos de `src/app` importan algo distinto de pantallas. Solución: mover la pantalla a `features/<feature>/ui` y dejar la ruta en dos líneas.

**Importar el interior de otra feature.** Se ve como `import { sqliteNotesRepository } from "@/features/notes/infrastructure/sqliteNotesRepository"` dentro de `features/quotes`. Ocurre porque el autocompletado del editor ofrece la ruta completa. Las features quedan acopladas y reorganizar una rompe la otra. Se detecta buscando imports de `features/<otra>/` que no terminen en el nombre de la feature. Solución: exportar lo necesario desde `index.ts`.

**Un `shared` que crece sin control.** Se ve como una carpeta `shared/` con la mitad del código de la app. Pasa porque todo lo que "quizá se reutilice" termina ahí. Se detecta cuando un archivo de `shared` solo lo usa una feature. Solución: el código vive en su feature hasta que una segunda feature lo necesite de verdad.
