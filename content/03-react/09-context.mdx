## Objetivo

Al terminar esta lección vas a poder crear un contexto con `createContext`, proveer un valor con un `Provider`, y leerlo desde cualquier componente anidado con `useContext`, sin pasarlo como prop en cada nivel intermedio.

**Prerrequisitos:** `03-react/08-composicion-y-container-presentational`

## Concepto

Imagina el juego del teléfono descompuesto: una persona susurra un mensaje a la siguiente, esa se lo pasa a la próxima, y así hasta el final de la fila. Cada persona en el medio tiene que repetir el mensaje aunque no le sirva de nada para sí misma, solo para que llegue a quien realmente lo necesita. Pasar una prop a través de varios niveles de componentes que no la usan, solo para que llegue a un componente muy anidado, se llama **prop drilling**, y sufre el mismo problema: cada componente intermedio tiene que aceptar y reenviar una prop que no le interesa.

```tsx
function App() {
  const theme = "dark";
  return <Page theme={theme} />;
}

function Page({ theme }: { theme: string }) {
  return <Sidebar theme={theme} />; // Page no usa theme, solo lo reenvía
}

function Sidebar({ theme }: { theme: string }) {
  return <ThemedButton theme={theme} />; // Sidebar tampoco lo usa
}

function ThemedButton({ theme }: { theme: string }) {
  return <button className={theme}>Botón</button>;
}
```

`Page` y `Sidebar` no hacen nada con `theme` salvo pasarlo hacia abajo. Cuantos más niveles agregues, más componentes intermedios quedan acoplados a una prop que no les pertenece.

### createContext y Provider

El **Context** de React resuelve esto: en lugar de una cadena de props, defines un canal directo entre un componente que provee un valor y cualquier componente descendiente que quiera leerlo, sin importar cuántos niveles haya en el medio.

```tsx
interface ThemeContextValue {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | null>(null);
```

`createContext` crea el "canal" en sí. El valor `null` que le pasas es el valor por defecto, usado solo si un componente lee el contexto sin que ningún `Provider` lo esté proveyendo más arriba en el árbol.

### Proveer el valor

```tsx
function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<"light" | "dark">("light");
  const toggleTheme = () => setTheme((current) => (current === "light" ? "dark" : "light"));

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>{children}</ThemeContext.Provider>
  );
}
```

`ThemeProvider` guarda el estado real (con `useState`, el hook que ya conoces) y lo entrega a través de `<ThemeContext.Provider value={...}>`. Cualquier componente dentro de `children`, sin importar la profundidad, puede leer ese valor.

### Leer el valor con un hook consumidor

En lugar de que cada componente escriba `useContext(ThemeContext)` y maneje el caso en que sea `null`, conviene envolver esa lectura en un custom hook propio:

```tsx
function useTheme() {
  const context = useContext(ThemeContext);
  if (!context) {
    throw new Error("useTheme debe usarse dentro de un ThemeProvider");
  }
  return context;
}
```

Este patrón combina dos temas que ya viste: `useContext` es un hook más, como `useState` o `useEffect`, y envolverlo en `useTheme` es exactamente la técnica de custom hooks de la lección anterior. El `throw` explícito convierte un bug silencioso (leer `theme` de un objeto `null`) en un error claro apenas alguien use `useTheme` fuera de un `ThemeProvider`.

```tsx
function ThemedButton() {
  const { theme, toggleTheme } = useTheme();
  return (
    <button className={theme} onClick={toggleTheme}>
      Tema actual: {theme}
    </button>
  );
}
```

`ThemedButton` puede estar anidado a cualquier profundidad dentro de `ThemeProvider` y accede al valor directamente, sin que ningún componente intermedio necesite saber que `theme` existe.

### Cuándo usar Context

Context es la herramienta correcta para valores que muchos componentes, a distintas profundidades, necesitan leer: el tema visual, el usuario autenticado, el idioma preferido. No es un reemplazo general del estado local: si solo un componente y sus hijos directos necesitan un valor, pasarlo como prop sigue siendo más simple y más fácil de rastrear. Herramientas más completas para manejar estado compartido entre muchas partes de la aplicación se ven en la etapa 5.

Documentación oficial: [react.dev/learn/passing-data-deeply-with-context](https://react.dev/learn/passing-data-deeply-with-context).

## Práctica

El siguiente Sandpack define `ThemeContext` con su `ThemeProvider` y el hook `useTheme`, y los usa desde un componente anidado a dos niveles de profundidad sin pasar ninguna prop manualmente.

```tsx
interface ThemeContextValue {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | null>(null);

function useTheme() {
  const context = useContext(ThemeContext);
  if (!context) throw new Error("useTheme debe usarse dentro de un ThemeProvider");
  return context;
}
```

<Sandpack
  files={{
    '/App.tsx': `import { createContext, useContext, useState } from "react";

interface ThemeContextValue {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | null>(null);

function useTheme() {
  const context = useContext(ThemeContext);
  if (!context) throw new Error("useTheme debe usarse dentro de un ThemeProvider");
  return context;
}

function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<"light" | "dark">("light");
  const toggleTheme = () => setTheme((current) => (current === "light" ? "dark" : "light"));
  return <ThemeContext.Provider value={{ theme, toggleTheme }}>{children}</ThemeContext.Provider>;
}

function ThemedButton() {
  const { theme, toggleTheme } = useTheme();
  return (
    <button
      onClick={toggleTheme}
      style={{
        background: theme === "light" ? "#eee" : "#222",
        color: theme === "light" ? "#111" : "#eee",
        padding: "8px 16px",
      }}
    >
      Tema actual: {theme}
    </button>
  );
}

function Sidebar() {
  // Sidebar no recibe ni reenvía theme como prop
  return (
    <div style={{ border: "1px solid #ccc", padding: 12 }}>
      <p>Panel lateral</p>
      <ThemedButton />
    </div>
  );
}

function Page() {
  return <Sidebar />;
}

export default function App() {
  return (
    <ThemeProvider>
      <Page />
    </ThemeProvider>
  );
}`,
  }}
/>

## Errores comunes

**Leer el contexto sin que ningún Provider lo esté proveyendo.** Si `ThemedButton` se renderiza fuera de `ThemeProvider`, `useContext(ThemeContext)` devuelve el valor por defecto que le diste a `createContext` (en el ejemplo, `null`), y el `throw` dentro de `useTheme` avisa de inmediato. Sin ese chequeo, el error aparecería más adelante y de forma más confusa, como "Cannot read properties of null".

**Crear un objeto nuevo como value en cada render sin necesidad.** Escribir `<ThemeContext.Provider value={{ theme, toggleTheme }}>` crea un objeto literal distinto en cada render de `ThemeProvider`, aunque `theme` no haya cambiado, lo que hace que todos los componentes que leen el contexto se vuelvan a renderizar también. Se detecta con las herramientas de perfilado de React viendo renders repetidos sin cambio real de datos; la solución, cuando se mide un problema real, es envolver el objeto en `useMemo`, como viste en la lección de `useRef, useMemo y useCallback`.

**Usar Context para cualquier estado, incluso el que solo necesita un componente y su hijo directo.** Envolver toda la aplicación en contextos para datos que solo dos componentes usan agrega una capa de indirección innecesaria: hay que abrir el archivo del contexto para entender de dónde sale un valor que una simple prop mostraría directamente en la firma del componente. Se detecta preguntando cuántos niveles de profundidad separan a quien provee el dato de quien lo consume; si es uno, una prop alcanza.
