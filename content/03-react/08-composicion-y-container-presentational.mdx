## Objetivo

Al terminar esta lección vas a poder separar un componente en una parte container (estado y lógica) y una parte presentational (solo props y JSX), y vas a poder explicar cuándo esa separación aporta valor y cuándo un custom hook ya resuelve lo mismo con menos código.

**Prerrequisitos:** `03-react/07-custom-hooks`

## Concepto

Piensa en un restaurante: en la cocina se decide qué ingredientes usar, se cocina y se emplata según la receta; en el salón, el mesero solo lleva el plato ya terminado a la mesa y lo presenta, sin decidir qué lleva la receta. Si cambias de proveedor de ingredientes, la cocina se adapta pero el mesero sigue haciendo exactamente lo mismo: mostrar el plato. El patrón **container/presentational** separa un componente de la misma forma: un componente **container** decide qué datos existen y cómo cambian (el estado, la lógica), y un componente **presentational** solo recibe esos datos como props y los muestra, sin saber de dónde vinieron.

### Presentational: solo props, sin estado propio de negocio

```tsx
interface Task {
  id: string;
  title: string;
  done: boolean;
}

function TaskList({ tasks, onToggle }: { tasks: Task[]; onToggle: (id: string) => void }) {
  return (
    <ul>
      {tasks.map((task) => (
        <li key={task.id}>
          <label>
            <input type="checkbox" checked={task.done} onChange={() => onToggle(task.id)} />
            {task.done ? <s>{task.title}</s> : task.title}
          </label>
        </li>
      ))}
    </ul>
  );
}
```

`TaskList` no tiene ningún `useState` propio relacionado con las tareas: recibe la lista completa y una función `onToggle`, y su única responsabilidad es transformar esos datos en JSX. Si le pasas datos distintos, muestra algo distinto; no le importa si esos datos vinieron de un array fijo, de una llamada a una API o de `localStorage`.

### Container: estado y lógica, delega el render

```tsx
function TaskListContainer() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: "t1", title: "Escribir informe", done: false },
    { id: "t2", title: "Revisar PR", done: true },
  ]);

  function handleToggle(id: string) {
    setTasks((previous) =>
      previous.map((task) => (task.id === id ? { ...task, done: !task.done } : task)),
    );
  }

  return <TaskList tasks={tasks} onToggle={handleToggle} />;
}
```

`TaskListContainer` no describe ningún `<ul>` ni ningún `<input>`: decide qué tareas existen y qué pasa cuando cambian, y le delega todo el JSX a `TaskList`. Esta separación trae dos beneficios concretos: puedes probar `TaskList` de forma aislada, pasándole datos de prueba directamente sin montar ninguna lógica de estado; y puedes reutilizar `TaskList` con otro container que obtenga las tareas de otro lado (por ejemplo, de una API), sin tocar una sola línea de la parte visual.

### Una separación de conceptos, no una regla rígida

Antes de que existieran los hooks, esta separación era casi la única forma práctica de reutilizar lógica de estado entre componentes sin duplicar código: si dos pantallas necesitaban la misma lógica de tareas, tenías que envolverla en un container o en patrones más complejos como los "higher-order components". Ya viste en la lección anterior que un **custom hook** como `useTasks()` puede encapsular exactamente esa misma lógica de estado y dártela como un array de valores y funciones, sin necesitar dos componentes ni dos archivos:

```tsx
function useTasks() {
  const [tasks, setTasks] = useState<Task[]>([]);
  function toggle(id: string) {
    setTasks((previous) =>
      previous.map((task) => (task.id === id ? { ...task, done: !task.done } : task)),
    );
  }
  return { tasks, toggle };
}

function TaskScreen() {
  const { tasks, toggle } = useTasks();
  return <TaskList tasks={tasks} onToggle={toggle} />;
}
```

Los hooks hicieron esta separación más liviana: ya no necesitas crear un componente container solo para tener un lugar donde poner el estado. Piensa en container/presentational como una manera de razonar sobre qué parte de tu código decide (estado, efectos, lógica) y qué parte solo muestra (props, JSX), no como una obligación de crear siempre dos archivos separados. Cuando el componente es simple y no vas a reutilizar la parte visual con otra fuente de datos, mezclar estado y JSX en un solo componente es perfectamente razonable.

Documentación oficial: [react.dev/learn/thinking-in-react](https://react.dev/learn/thinking-in-react).

## Práctica

El siguiente Sandpack separa `TaskListContainer` (estado) de `TaskList` (solo props), e incluye un segundo container, `CompletedCountContainer`, que reutiliza una versión de solo lectura de la lista para mostrar cuántas tareas están hechas, demostrando que la parte presentational sirve para más de un container.

```tsx
interface Task {
  id: string;
  title: string;
  done: boolean;
}

function TaskList({ tasks, onToggle }: { tasks: Task[]; onToggle: (id: string) => void }) {
  return (
    <ul>
      {tasks.map((task) => (
        <li key={task.id}>
          <label>
            <input type="checkbox" checked={task.done} onChange={() => onToggle(task.id)} />
            {task.done ? <s>{task.title}</s> : task.title}
          </label>
        </li>
      ))}
    </ul>
  );
}
```

## Errores comunes

**Duplicar estado en el componente presentational.** Si `TaskList` guardara su propia copia de `tasks` con `useState` en lugar de leerla siempre desde props, esa copia se desincroniza en cuanto el container actualiza su propio estado, porque nada conecta ambas copias automáticamente. Se detecta porque la interfaz muestra datos distintos según qué copia se renderizó, y actualizar una no actualiza la otra.

**Mezclar lógica de fetch o de negocio dentro del componente presentational.** Si `TaskList` llamara directamente a una API para obtener las tareas, ya no podrías reutilizarlo con datos de prueba ni con otra fuente de datos sin reescribirlo. Se detecta revisando si el componente que solo debería "mostrar" tiene código que decide de dónde vienen los datos.

**Dividir en container y presentational cuando no hay ninguna necesidad de reutilización.** Crear dos componentes y dos archivos para un botón con un solo `useState` que nunca se va a reutilizar en otro contexto agrega indirección sin beneficio real. Se detecta preguntando: ¿voy a mostrar esta misma UI con otra fuente de datos, o necesito probar la parte visual de forma aislada? Si la respuesta es no en ambos casos, un custom hook o un solo componente suele bastar.
