## Objetivo

Al terminar esta lección vas a poder instalar TypeScript en un proyecto, generar un `tsconfig.json` con `tsc --init`, y explicar qué exige activar `strict: true`.

**Prerrequisitos:** `02-typescript/06-utility-types`

## Concepto

Piensa en las reglas de seguridad de una obra de construcción. En una obra sin supervisión, cada trabajador decide si usa casco. En una obra con inspección estricta, el casco es obligatorio y un inspector lo revisa antes de dejar entrar a nadie. `strict: true` en TypeScript es esa inspección: activa, de una sola vez, un conjunto de reglas que en conjunto atrapan la mayoría de los errores de tipos que este curso viene mostrando. Desde TypeScript 6.0, `strict` ya viene activado por defecto; aun así, este curso lo escribe de forma explícita en `tsconfig.json`, porque muchos proyectos y herramientas todavía usan versiones anteriores, donde esas reglas estaban apagadas si no las pedías.

### El archivo `tsconfig.json`

`tsconfig.json` es el archivo de configuración que le dice a `tsc` cómo compilar un proyecto: qué archivos incluir, a qué versión de JavaScript compilar, y qué reglas de revisión aplicar. Se genera con:

```
npx tsc --init
```

Esto crea un `tsconfig.json` con opciones activas y otras comentadas. Con la versión actual de TypeScript, las que importan para este curso son pocas:

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "target": "esnext",
    "strict": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true
  }
}
```

`module: "nodenext"` y `target: "esnext"` generan JavaScript moderno con módulos ES, como los que usaste en la etapa 1; `verbatimModuleSyntax` exige que los imports que solo traen tipos se marquen con `import type`. El archivo generado incluye además otras reglas extra de seguridad (por ejemplo `noUncheckedIndexedAccess`) que puedes dejar activas.

### Qué activa `strict: true`

`strict` no es una sola regla: es un interruptor que enciende varias a la vez. Las tres más relevantes para lo aprendido en esta etapa:

- **`noImplicitAny`**: si una variable o parámetro no tiene anotación de tipo y TypeScript no puede inferirlo, en vez de asumir `any` en silencio, marca un error. Esto evita que código sin anotar se cuele como `any` sin que nadie lo note.
- **`strictNullChecks`**: `null` y `undefined` dejan de ser asignables a cualquier tipo. Sin esta regla, una variable `string` podría contener `null` sin ningún aviso, y fallaría en tiempo de ejecución al llamar un método sobre ella. Con la regla activa, si una variable puede ser `null`, tiene que anotarse explícitamente como `string | null`, y el compilador exige comprobarlo antes de usarla, igual que con `unknown` en la lección 1.
- **`strictPropertyInitialization`**: en una clase, una propiedad declarada sin valor inicial y sin marcar como opcional debe inicializarse en el constructor. Evita propiedades que quedan en `undefined` sin que el tipo lo refleje.

Sin `strict`, TypeScript revisa mucho menos de lo que parece: acepta código que en la práctica esconde los mismos errores que JavaScript. Activar `strict: true` desde el inicio de un proyecto es más simple que activarlo después, cuando ya hay cientos de líneas que dependían de las reglas apagadas. Documentación oficial: [tsconfig Reference](https://www.typescriptlang.org/tsconfig).

### Compilar el proyecto

```
npx tsc
```

Sin argumentos, `tsc` lee `tsconfig.json`, compila todos los archivos `.ts` incluidos, y termina sin imprimir nada si no hay errores. Si hay errores de tipos, los lista con archivo, línea y columna. Por defecto igual genera el JavaScript de salida; si quieres que no lo haga mientras haya errores, activa `noEmitOnError: true`.

## Errores comunes

**Dejar `strict: false` "por ahora" y nunca volver a activarlo.** Cada línea escrita sin `strict` puede depender, sin saberlo, de que TypeScript no revise `null` o no marque `any` implícitos. Activarlo después obliga a corregir todo el código acumulado de una vez. Cómo detectarlo: abre `tsconfig.json` y busca `"strict"`; si no aparece o está en `false`, el proyecto no tiene la protección completa.

**Confundir errores de `tsc` con errores del `Playground`.** Como se explicó en la lección 0, el `Playground` de esta plataforma no ejecuta `tsc`: solo quita tipos con Sucrase. Los pasos de esta lección (`npx tsc --init`, `npx tsc`) son comandos reales de una terminal, no algo que el `Playground` reproduzca. Cómo detectarlo: si esperas ver un error de `tsc` dentro de un `Playground`, no vas a verlo; usa una terminal real o el editor.

**Ignorar el código de salida de `npx tsc`.** `tsc` no imprime nada cuando compila sin errores, lo cual puede confundirse con que "no hizo nada". Cómo detectarlo: revisa el código de salida del comando (`echo $?` en una terminal Unix); `0` significa éxito, cualquier otro valor indica que hubo errores de compilación.
