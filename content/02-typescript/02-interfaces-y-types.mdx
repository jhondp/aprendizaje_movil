## Objetivo

Al terminar esta lección vas a poder definir la forma de un objeto con `interface` y con `type`, marcar campos opcionales y explicar cuándo elegir cada una.

**Prerrequisitos:** `02-typescript/01-tipos-basicos`

## Concepto

Un contrato de alquiler describe qué debe tener un departamento antes de firmarlo: cuántas habitaciones, si tiene balcón, cuál es la dirección. No importa el departamento concreto que finalmente ocupes, mientras cumpla ese contrato. Una **interface** en TypeScript es exactamente eso: un contrato que describe qué forma debe tener un objeto, sin importar cuál sea el objeto concreto.

### `interface`

```ts
interface Task {
  id: number;
  title: string;
  done: boolean;
}

const task: Task = {
  id: 1,
  title: "Comprar leche",
  done: false,
};
```

Cualquier objeto que tenga esas tres propiedades, con esos tipos, cumple el contrato `Task`. Si falta una propiedad, o su tipo no coincide, el compilador lo rechaza:

```ts
const invalid: Task = {
  id: 1,
  title: "Comprar leche",
}; // error: falta la propiedad done
```

### Campos opcionales

No todos los campos de un objeto son obligatorios siempre. Un signo de interrogación después del nombre marca un campo como opcional:

```ts
interface Task {
  id: number;
  title: string;
  done: boolean;
  notes?: string;
}

const withNotes: Task = { id: 2, title: "Llamar al dentista", done: false, notes: "Turno de la tarde" };
const withoutNotes: Task = { id: 3, title: "Leer un capítulo", done: true };
```

Ambos objetos son válidos: `notes` puede estar presente o ausente, pero si está presente debe ser un `string`. Dentro del código, `task.notes` tiene tipo `string | undefined` (una unión, tema de la próxima lección), así que antes de usarlo como texto hay que comprobar que no sea `undefined`.

### `type`: el alias de tipo

`type` declara un nombre para cualquier tipo, incluida la forma de un objeto:

```ts
type Task = {
  id: number;
  title: string;
  done: boolean;
};
```

Para describir la forma de un objeto plano, `interface` y `type` hacen prácticamente lo mismo y ambas son correctas; la elección suele ser una convención de equipo. La diferencia real aparece en lo que cada una puede expresar además de objetos: `type` también nombra uniones (`type Id = string | number`) y tuplas, algo que `interface` no puede hacer directamente; `interface` en cambio permite que dos declaraciones con el mismo nombre se combinen (declaration merging) y se extiende con `extends` de una forma más directa para jerarquías de objetos.

La recomendación práctica para este curso: usa `interface` para la forma de un objeto (una `Task`, un `User`) y `type` cuando necesites nombrar una unión o un alias que no es un objeto. Ambas son válidas y verás las dos en proyectos reales; lo importante es ser consistente dentro de un mismo equipo. Documentación oficial: [Everyday Types — Object Types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#object-types).

## Errores comunes

**Crear un objeto sin todas las propiedades obligatorias.** Si `Task` exige `id`, `title` y `done`, y el objeto solo trae dos, el compilador lo rechaza con un mensaje del tipo "Property 'done' is missing". Cómo detectarlo: el error nombra exactamente la propiedad faltante.

**Usar un campo opcional sin comprobar si está presente.** `task.notes.toUpperCase()` falla en tiempo de ejecución cuando `notes` es `undefined`, aunque compile si el tipo aún no fue acotado. Cómo detectarlo: el compilador exige, antes de esa línea, algo como `if (task.notes)` o `task.notes?.toUpperCase()`; si no lo pusiste, el editor marca el acceso como inseguro.

**Mezclar `interface` y `type` sin criterio dentro del mismo equipo.** No es un error de compilación, pero un archivo con `interface Task` en una línea y `type User = {...}` en la siguiente, sin ninguna razón para la diferencia, dificulta la lectura. Cómo detectarlo: revisa si el equipo tiene una convención documentada; si no la tiene, es momento de acordarla.
