## Objetivo

Al terminar esta lección vas a poder migrar un programa JavaScript existente a TypeScript de forma incremental, tipando su estado con `interface` y `type`, y comprobando que compila sin errores con `strict: true`.

**Prerrequisitos:** `02-typescript/07-strict-mode-y-tsconfig`

## Concepto

Piensa en renovar una casa mientras sigues viviendo en ella: no la demoles entera de un día para otro, renuevas una habitación, compruebas que todo sigue funcionando, y sigues con la siguiente. Migrar un proyecto JavaScript a TypeScript se hace igual: no se reescribe todo de golpe, se avanza pieza por pieza, comprobando con `tsc` después de cada cambio que nada quedó roto.

Esta lección retoma la app de tareas en consola de `01-javascript/13-proyecto-app-de-tareas` y la convierte en `todo.ts`, aplicando todo lo aprendido en esta etapa: `interface` para el objeto `Task`, `type` para los estados válidos, genéricos donde hace falta reutilizar lógica, narrowing en las ramas, utility types para no repetir formas ya declaradas, y `strict: true` como red de seguridad final.

### El punto de partida en JavaScript

La versión original no distingue qué valores son válidos para filtrar la lista: `filter` es un `string` cualquiera.

```js
let nextId = 1;
const tasks = [];

function addTask(title) {
  const task = { id: nextId, title, done: false };
  nextId += 1;
  tasks.push(task);
  return task;
}

function toggleTask(id) {
  const task = tasks.find((t) => t.id === id);
  if (task) {
    task.done = !task.done;
  }
}

function listTasks(filter) {
  if (filter === "pending") return tasks.filter((t) => !t.done);
  if (filter === "done") return tasks.filter((t) => t.done);
  return tasks;
}
```

Nada impide llamar `listTasks("pendiente")` con una falta de ortografía: como ninguno de los dos `if` coincide, la función devuelve silenciosamente todas las tareas, y el error pasa inadvertido hasta que alguien nota que el filtro "no filtra nada".

### La misma app en TypeScript

```ts
interface Task {
  id: number;
  title: string;
  done: boolean;
}

type Filter = "all" | "pending" | "done";

let nextId = 1;
const tasks: Task[] = [];

function addTask(title: string): Task {
  const task: Task = { id: nextId, title, done: false };
  nextId += 1;
  tasks.push(task);
  return task;
}

function toggleTask(id: number): void {
  const task = tasks.find((t) => t.id === id);
  if (task) {
    task.done = !task.done;
  }
}

function listTasks(filter: Filter): Task[] {
  if (filter === "pending") return tasks.filter((t) => !t.done);
  if (filter === "done") return tasks.filter((t) => t.done);
  return tasks;
}
```

Tres cambios concretos, cada uno de una lección anterior:

- `interface Task` (lección 2) documenta la forma exacta de una tarea: sin ella, `tasks.push(task)` aceptaría cualquier objeto, con ella el compilador rechaza uno al que le falte `done`.
- `type Filter = "all" | "pending" | "done"` (lección 3) reemplaza el `string` libre de `filter`. Ahora `listTasks("pendiente")` no compila: `Argument of type '"pendiente"' is not assignable to parameter of type 'Filter'.` El error de tipeo se detecta antes de ejecutar, no después de que alguien reporte que el filtro no funciona.
- `const tasks: Task[] = []` anota el array vacío. Sin la anotación, TypeScript no tiene forma de saber qué vas a guardar ahí y lo infiere como `any[]`, perdiendo toda revisión sobre lo que se agrega con `push`.

Ninguna función cambió su lógica: cada `if` y cada `return` son idénticos a la versión JavaScript. Migrar no significa reescribir el comportamiento, significa anotar lo que el comportamiento ya asumía en silencio.

### Reutilizar formas con utility types

Cuando una función solo necesita parte de `Task`, conviene derivarla en vez de declarar una interfaz nueva. Para crear una tarea, `id` lo genera `addTask` y `done` siempre arranca en `false`, así que quien llama a la función solo debería poder pasar `title`:

```ts
function createTask(input: Omit<Task, "id" | "done">): Task {
  const task: Task = { id: nextId, ...input, done: false };
  nextId += 1;
  return task;
}
```

`Omit<Task, "id" | "done">` (lección 6) es, en este caso, exactamente `{ title: string }`, pero declararlo así dice explícitamente "esto es Task sin id ni done", y si mañana `Task` gana un campo nuevo, `createTask` lo hereda sin que nadie tenga que tocar esta firma.

### Compilar y confirmar

Con el `tsconfig.json` de la lección anterior (`strict: true`), correr `npx tsc` sobre `todo.ts` debe terminar sin imprimir nada. Si aparecen errores, lee el primero de la lista: el compilador señala archivo, línea y columna exactos, igual que en la lección 0. Corregir el primero a menudo hace desaparecer otros que dependían de él. La guía oficial para este proceso, con más casos que los que cubre esta lección, está en [Migrating from JavaScript](https://www.typescriptlang.org/docs/handbook/migrating-from-javascript.html).

## Errores comunes

**Dejar el estado sin anotar (`const tasks = []`).** Un array vacío sin anotación ni contexto que lo aclare se infiere como `any[]`, así que `tasks.push(42)` no produce ningún error aunque el resto del programa espere `Task`. Cómo detectarlo: revisa la declaración de `tasks`; si no dice `: Task[]`, el editor no distingue esa lista de un array de cualquier cosa.

**Pasar un string cualquiera donde se espera un `Filter`.** Antes de migrar, `listTasks("pendiente")` compilaba y fallaba en silencio; después de migrar, con `filter: Filter`, esa misma llamada no compila. Cómo detectarlo: el mensaje dice `Argument of type '"pendiente"' is not assignable to parameter of type 'Filter'`, señalando el literal exacto que sobra.

**Anotar donde ya se infiere y dejar sin anotar donde realmente hace falta.** Escribir `const first: Task = tasks[0]` cuando `tasks` ya es `Task[]` es ruido innecesario, porque TypeScript ya lo infiere; en cambio, dejar sin tipo el parámetro de una función usada por otro archivo sí pierde protección real. Cómo detectarlo: con `noImplicitAny` (lección 7) activo, un parámetro de función sin tipo y sin forma de inferirlo marca error de inmediato; una variable local cuyo tipo ya es evidente por el valor asignado, no.
