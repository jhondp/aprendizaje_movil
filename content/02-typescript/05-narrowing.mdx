## Objetivo

Al terminar esta lección vas a poder reducir el tipo de una variable dentro de una rama de código usando `typeof` y `in`, y escribir un `switch` exhaustivo que el compilador verifica por ti.

**Prerrequisitos:** `02-typescript/04-genericos`

## Concepto

Piensa en un guardia de seguridad frente a dos puertas distintas, una para empleados y otra para visitantes. Antes de dejar pasar a alguien, el guardia comprueba la credencial: si es de empleado, abre la puerta de empleados; si es de visitante, abre la otra. La credencial concreta que tiene la persona en la mano determina qué puerta se abre. **Narrowing** es ese mismo proceso aplicado a tipos: TypeScript reduce (acota) el tipo posible de una variable dentro de una rama de código, según una comprobación que hiciste antes.

### `typeof`

Para valores primitivos, `typeof` es la comprobación más directa:

```ts
function formatId(id: string | number): string {
  if (typeof id === "string") {
    return id.toUpperCase(); // aquí TypeScript sabe que id es string
  }
  return id.toFixed(0); // aquí sabe que id es number
}
```

Dentro del `if`, TypeScript reduce `id` de `string | number` a solo `string`, y permite `toUpperCase()`. En la rama `return` final, ya descartó `string`, así que `id` solo puede ser `number`, y permite `toFixed()`. Ninguna de las dos llamadas sería válida fuera de su rama correspondiente.

### `in`

Para distinguir entre dos formas de objeto que no comparten un discriminante explícito, el operador `in` comprueba si una propiedad existe:

```ts
interface Circle {
  radius: number;
}

interface Rectangle {
  width: number;
  height: number;
}

function area(shape: Circle | Rectangle): number {
  if ("radius" in shape) {
    return Math.PI * shape.radius ** 2; // aquí TypeScript sabe que shape es Circle
  }
  return shape.width * shape.height; // aquí sabe que shape es Rectangle
}
```

`"radius" in shape` comprueba, en tiempo de ejecución, si el objeto tiene esa propiedad, y TypeScript usa esa misma comprobación para reducir el tipo en cada rama.

### `switch` exhaustivo sobre un discriminante

La lección anterior mostró uniones discriminadas con un campo `kind`. Un `switch` sobre ese campo, combinado con el tipo `never`, permite que el compilador te avise si olvidaste cubrir un caso:

```ts
type Status = "todo" | "in-progress" | "done";

function label(status: Status): string {
  switch (status) {
    case "todo":
      return "Por hacer";
    case "in-progress":
      return "En progreso";
    case "done":
      return "Hecha";
    default: {
      const exhaustiveCheck: never = status;
      return exhaustiveCheck;
    }
  }
}
```

Si mañana alguien agrega un cuarto valor a `Status`, por ejemplo `"archived"`, y no actualiza el `switch`, la línea `const exhaustiveCheck: never = status` deja de compilar: dentro del `default`, `status` ya no sería `never` (el tipo de "esto nunca debería ocurrir"), sería `"archived"`, y asignar un `string` a `never` es un error. Este patrón convierte un olvido silencioso, el tipo de bug que solo se nota en producción, en un error de compilación inmediato. Documentación oficial: [Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html).

## Errores comunes

**Comprobar `typeof` con un valor incorrecto.** `typeof id === "String"` (con mayúscula) o `typeof id === "text"` nunca es verdadero, porque `typeof` siempre devuelve minúsculas exactas: `"string"`, `"number"`, `"boolean"`, `"undefined"`, `"object"`, `"function"`. Cómo detectarlo: el compilador marca la comparación con `TS2367: This comparison appears to be unintentional because the types '"string" | "number" | ...' and '"String"' have no overlap.`; corrige el texto a minúsculas exactas.

**Usar `in` sobre una propiedad que ambos tipos comparten.** Si `Circle` y `Rectangle` tuvieran ambas una propiedad `color`, comprobar `"color" in shape` no distingue nada, porque es verdadero para las dos formas. Cómo detectarlo: dentro del `if`, TypeScript no reduce la unión a un solo tipo, porque la propiedad no es exclusiva de una forma.

**Olvidar el caso `default` con `never` y perder la verificación de exhaustividad.** Si la función declara un tipo de retorno como `string`, `tsc --strict` ya avisa cuando falta un caso, pero con un mensaje genérico: `TS2366: Function lacks ending return statement and return type does not include 'undefined'.` El patrón `never` importa sobre todo en funciones que devuelven `void` (por ejemplo, un `switch` que solo imprime o actualiza estado), donde un caso olvidado no produce ningún error, y además nombra el valor que falta: `Type '"archived"' is not assignable to type 'never'.` Cómo detectarlo: agrega un valor nuevo a la unión y revisa si el compilador señala cada `switch` incompleto; si alguno no aparece, le falta el `default` con `never`.
