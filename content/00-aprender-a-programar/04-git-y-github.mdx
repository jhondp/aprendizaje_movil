## Objetivo

Al terminar esta lección vas a poder crear un repositorio Git, guardar cambios en commits y subirlos a un repositorio remoto en GitHub.

**Prerrequisitos:** `00-aprender-a-programar/03-vs-code-y-node`

## Concepto

Imagina que escribes un documento y cada tanto guardas una copia con fecha, para poder volver atrás si algo sale mal. Eso es, en esencia, lo que hace **Git**: una herramienta que guarda "fotografías" del estado de tu proyecto a lo largo del tiempo, para que puedas ver qué cambió, cuándo y por qué, y volver a una versión anterior si lo necesitas.

Cuatro palabras que vas a usar todo el curso:

- **Repositorio**: una carpeta cuyos cambios Git está rastreando. Se crea con `git init`.
- **Commit**: una fotografía del proyecto en un momento dado, con un mensaje que explica qué cambió. Los commits son la unidad básica de historia en Git.
- **Rama (branch)**: una línea de historia dentro del repositorio. La rama por defecto se llama `main`, y en este curso vas a trabajar siempre sobre ella salvo que se indique lo contrario.
- **Remoto (remote)**: una copia del repositorio alojada en otro lugar, normalmente en un servidor. **GitHub** es el sitio donde vas a alojar tus remotos: además de guardar una copia de respaldo en internet, te permite mostrar tu trabajo y, más adelante en el curso, colaborar con otras personas.

### El flujo básico

1. `git init` crea un repositorio Git nuevo en la carpeta actual.
2. `git add <archivo>` marca los cambios de ese archivo para que entren en el próximo commit (a esto se lo llama "staging", preparar los cambios).
3. `git commit -m "mensaje"` guarda esos cambios preparados como un commit, con el mensaje que describe qué hiciste.
4. `git remote add origin <url>` conecta tu repositorio local con uno remoto en GitHub, y lo llama `origin` (el nombre por convención del remoto principal).
5. `git push -u origin main` sube tus commits al remoto. El flag `-u` (upstream) recuerda esa conexión, así que las próximas veces alcanza con `git push`.

### Autenticarte con GitHub

Cuando subes cambios por HTTPS (la URL empieza con `https://`), GitHub ya no acepta la contraseña de tu cuenta como método de autenticación. En su lugar, usas un **token de acceso personal** (personal access token): una clave que generas desde la configuración de tu cuenta de GitHub y que pegas cuando se te pida la contraseña. En este curso vas a usar siempre remotos HTTPS con token, no SSH, porque no requiere configurar claves adicionales en tu computadora. Puedes ver el paso a paso oficial para crear un token en [docs.github.com/es/get-started](https://docs.github.com/es/get-started) y repasar el flujo completo de Git en el [Pro Git Book](https://git-scm.com/book/es/v2).

<Callout kind="warning">
  Guarda tu token de acceso personal en un lugar seguro apenas lo generes: GitHub solo lo muestra una vez.
</Callout>

## Errores comunes

- **Hacer `git commit` sin haber hecho `git add` antes.** Git responde algo como "nothing to commit, working tree clean" aunque hayas editado archivos. Cómo detectarlo: ejecuta `git status` antes del commit para ver qué está preparado (en verde) y qué no (en rojo).
- **Configurar un remoto SSH sin tener una clave SSH generada.** El push falla con un error de permisos ("Permission denied (publickey)"). Cómo detectarlo: si tu URL remota empieza con `git@github.com:`, es SSH; cámbiala por la versión HTTPS (`https://github.com/...`).
- **Escribir mensajes de commit que no dicen nada, como "cambios" o "fix".** Dentro de unas semanas no vas a recordar qué se corrigió. Cómo detectarlo: si el mensaje no te permite adivinar qué cambió sin mirar el código, reescríbelo.
- **Olvidar `-u` en el primer push.** Los próximos `git push` fallan pidiendo que especifiques la rama remota. Cómo detectarlo: el mensaje sugiere ejecutar `git push --set-upstream origin main`; hazlo una vez y los próximos push funcionan sin el flag.
